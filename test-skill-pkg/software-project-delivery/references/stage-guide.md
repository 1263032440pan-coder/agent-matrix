# 九阶段执行手册

每阶段的标准操作流程：输入 → 步骤 → 输出 → 自检 → 常见错误。

---

## 阶段 1：项目理解

**输入**：用户提供的项目材料（md）。

**步骤**：
1. 通读全文，标记所有"必须/不做/禁止/要求"语句；
2. 判定项目类型与规模（对照：小型本地工具 / 中型服务端应用 / 内容型项目）；
3. 列出目标用户与运行环境约束；
4. 盘点已有信息 vs 缺失信息（解决方案？需求基线？架构？代码？）——**缺失就是缺失，不得伪造**。

**输出**：项目理解摘要。

**自检清单**：
- [ ] 项目类型判定有依据（引用材料原文）
- [ ] 约束清单逐条可回溯到材料原文
- [ ] 信息缺口如实列出

**常见错误**：把"应该有架构文档"当成"已有架构文档"；遗漏"明确不实现"清单。

## 阶段 2：需求基线

**输入**：项目理解摘要 + 原始材料。

**步骤**：
1. 功能需求逐条提取编号（FR-001…），每条写：描述 / 本期必须或明确不做 / 验收标准；
2. 非功能需求归类（性能、环境、安全、可维护性）；
3. 边界场景穷举（空标题、非法状态、不存在的任务、接口失败、数据库失败）；
4. 与材料逐条对照查漏。

**输出**：需求文档。

**自检清单**：
- [ ] 材料每条"必须实现"都有 FR 编号
- [ ] "明确不实现"完整照搬（一条不少）
- [ ] 每条 FR 的验收标准可测试（不是"做好"这种虚词）

**常见错误**：擅自增加材料没有的功能；验收标准不可测试。

## 阶段 3：解决方案

**输入**：需求文档。

**步骤**：
1. 一段话方案概述；
2. 技术栈表——每项**唯一**：前端框架+版本 / 后端框架+版本 / 语言+版本 / 数据库+版本 / ORM / 测试框架 / 构建方式 / 启动方式；
3. 每项选型写一句话理由（与项目约束的匹配点）；
4. 分层职责说明。

**输出**：解决方案文档。

**自检清单**：
- [ ] 技术栈表 8 项全部唯一确定
- [ ] 无"A 或 B 均可 / 后续再决定 / 任选"
- [ ] 选型与"本地单机运行"约束一致

**常见错误**：留双选；选型理由空泛（"流行"不算理由）。

## 阶段 4：原型设计

**输入**：需求文档 + 解决方案。

**步骤**：
1. 页面布局线框（文本框图，标注各区块职责）；
2. 新建/编辑的交互形态确定（弹窗或抽屉二选一）；
3. 删除确认形式确定；
4. 搜索/筛选/统计控件的位置与行为。

**输出**：系统原型图 + 交互说明。

**自检清单**：
- [ ] 布局覆盖材料第 6 节页面要求（若有）
- [ ] 交互形态全部唯一确定
- [ ] 统计区字段与需求一致

## 阶段 5：架构设计

**输入**：需求 + 解决方案 + 原型。

**步骤**：
1. 模块划分（前端组件树 / 后端 router-service-model 分层）；
2. 数据模型：建表 DDL 级别的字段定义（名/类型/约束/默认值/索引）；
3. API 契约：每个接口 Method + URL + 请求/响应 Schema + 错误码；
4. 业务流程图（主流程 + 异常分支）。

**输出**：系统架构文档。

**自检清单**：
- [ ] 表结构字段覆盖需求全部字段（含时间戳）
- [ ] API 覆盖全部 FR（增删改查 + 统计 + 搜索筛选参数）
- [ ] 错误码有明确定义（400 类校验错 / 404 不存在 / 500 内部）
- [ ] 无单文件大杂烩设计

**常见错误**：API 忘记统计接口；表结构缺 updated_at；筛选条件没进查询参数。

## 阶段 6：开发实现

**输入**：架构文档。

**步骤**：
1. 数据层：建表 + ORM 模型 + 连接配置；
2. 后端：按契约实现 API + 输入校验 + 统一错误响应；
3. 前端：页面布局 + 列表 + 表单（新建/编辑）+ 删除确认 + 搜索筛选 + 统计条 + 失败提示；
4. 开发文档：目录结构 + 模块清单 + 启动步骤。

**输出**：源码 + 开发文档。

**自检清单**：
- [ ] 按使用文档命令能一键启动
- [ ] 每个错误场景返回明确 Error Code + message
- [ ] 前端所有接口调用有失败提示路径
- [ ] 代码结构与架构文档一致

**常见错误**：只写 happy path；校验只在前端做；启动步骤缺依赖安装。

## 阶段 7：测试验证

**输入**：源码 + 需求验收清单。

**步骤**：
1. 后端测试逐条写（对应需求边界场景）；
2. 前端核心路径测试；
3. E2E 闭环脚本（启动→创建→查→改状态→改完成→统计→删→确认不存在）；
4. 跑全部测试，记录结果成报告。

**输出**：测试代码 + 测试报告。

**自检清单**：
- [ ] 后端测试覆盖：创建/查询/修改/删除/非法状态/非法优先级/不存在/统计
- [ ] E2E 闭环完整跑通
- [ ] 测试报告含用例清单与执行结果，失败项标注

**常见错误**：只测 happy path；E2E 用 mock 数据绕过真实启动。

## 阶段 8：交付打包

**输入**：前七阶段全部产物。

**步骤**：
1. 对照十项交付清单盘点（源码/解决方案/需求/原型/流程图/架构/开发文档/测试报告/交付文档/使用文档）；
2. 缺什么补什么；
3. 使用文档面向**最终用户**写（环境/安装/启动/怎么用，非开发者视角）；
4. 交付文档含版本说明 + 交付物清单 + 已知限制。

**输出**：交付文档 + 使用文档。

**自检清单**：
- [ ] 十项交付物全部存在
- [ ] 使用文档步骤可照做启动
- [ ] 已知限制如实列出

## 阶段 9：Final Gate

**输入**：全部交付物。

**步骤**（逐项检查，引用证据）：
1. 开发完成？→ 引用启动验证记录；
2. 测试通过？→ 引用测试报告结论；
3. 文档齐备？→ 引用交付清单核对结果；
4. 使用文档可用？→ 引用按步骤启动的验证；
5. 验收标准逐条核对？→ 对照需求文档验收清单逐项勾选。

**输出**：Final Gate 检查记录。

**判定规则**：
- 全部满足 → Project Completed；
- 任一不满足 → **REWORK**，检查记录必须明确指出缺口与建议修复动作；
- **禁止**以"代码写完"替代完成判定。
