# 质量门（Gate）验收细则

每阶段 Gate 的判定标准与 REWORK 规则。Reviewer/Gate 按此逐项检查 Artifact。

---

## 通用规则

1. **证据导向**：每项检查必须能指向 Artifact 中的具体内容，不接受"已完成"的自述；
2. **REWORK 判定**：任一必检项不满足 → 整体 REWORK，意见中**明确指出缺口与建议动作**；
3. **约束优先**：项目输入材料的明确约束优先于本细则——若材料规定了更严的标准，以材料为准；
4. **禁止越权**：Gate 只做验收判定与 ACCEPTED/REWORK 转移，不直接修改 Artifact。

## 阶段 1 Gate：项目理解

| 必检项 | 判定 |
|---|---|
| 项目类型判定 | 与材料特征一致（如小型软件开发项目） |
| 约束清单完整性 | 材料中每条"必须/不做/禁止"都被收录 |
| 信息缺口如实 | 没有伪造"已有"的解决方案/需求/架构/代码 |

**REWORK 示例意见**：「约束清单遗漏材料第 12 节'本期明确不实现'中的任务评论等 13 项，请补齐后重新提交。」

## 阶段 2 Gate：需求基线

| 必检项 | 判定 |
|---|---|
| FR 覆盖 | 材料"必须实现"清单逐条有 FR 编号 |
| 排除项完整 | "明确不实现"清单完整照搬 |
| 验收标准可测 | 无"做好/合理"类虚词，每条可执行验证 |
| 边界场景 | 至少覆盖：空标题/不存在/非法状态/非法优先级/接口失败/数据库失败 |

## 阶段 3 Gate：解决方案

| 必检项 | 判定 |
|---|---|
| 技术栈唯一 | 8 项选型（前端/后端/语言/数据库/ORM/测试/构建/启动）每项唯一且带版本 |
| 无悬空决策 | 不存在"均可/再定/任选" |
| 选型匹配 | 与运行环境约束一致（本地单机 → 不选需要 K8s 的方案） |

**REWORK 示例意见**：「技术栈表中数据库一项仍为'SQLite 或 PostgreSQL 均可'，违反唯一化要求；请结合单机场景确定其一并写明理由。」

## 阶段 4 Gate：原型

| 必检项 | 判定 |
|---|---|
| 页面结构 | 覆盖材料的页面要求（布局区块齐全） |
| 交互唯一 | 新建/编辑形式、删除确认形式均已确定 |

## 阶段 5 Gate：架构

| 必检项 | 判定 |
|---|---|
| 数据模型 | 字段覆盖需求全部字段（含 created/updated 时间戳） |
| API 完整 | 覆盖全部 FR：增删改查 + 统计 + 搜索/筛选参数 |
| 错误码 | 400/404/500 语义明确列出 |
| 模块划分 | 前后端分层，无单文件大杂烩 |

## 阶段 6 Gate：开发

| 必检项 | 判定 |
|---|---|
| 可启动 | 按文档命令能启动（或提供可核对的启动验证记录） |
| 校验落地 | 后端存在标题必填/枚举校验的代码证据 |
| 错误响应 | 统一错误格式，含 Error Code |
| 前端提示 | 接口失败有用户可见提示的代码路径 |
| 结构一致 | 目录结构与架构文档的模块划分一致 |

## 阶段 7 Gate：测试

| 必检项 | 判定 |
|---|---|
| 后端用例 | 覆盖：创建/查询/修改/删除/非法状态/非法优先级/不存在/统计 |
| E2E 闭环 | 至少一条真实闭环（创建→…→删除→确认不存在）通过 |
| 测试报告 | 用例清单 + 执行结果齐备 |
| 无阻塞缺陷 | 报告中不存在标为"阻塞级"的未修复问题 |

**REWORK 示例意见**：「E2E 闭环缺失'确认删除后任务不存在'断言，测试未证明删除真实生效，请补全后重跑。」

## 阶段 8 Gate：交付

| 必检项 | 判定 |
|---|---|
| 十项清单 | 源码/解决方案/需求/原型/流程图/架构/开发文档/测试报告/交付文档/使用文档全部存在 |
| 使用文档视角 | 面向最终用户（环境/安装/启动/用法），非开发者内部文档 |

## 阶段 9：Final Gate（项目完成判定）

**全部满足才允许 Project Completed**：

| # | 检查 | 证据要求 |
|---|---|---|
| 1 | 开发完成 | 启动验证记录 |
| 2 | 后端测试通过 | 测试报告结论 |
| 3 | 前端测试通过 | 测试报告结论 |
| 4 | E2E 通过 | 闭环执行记录 |
| 5 | 交付文档齐备 | 十项清单核对结果 |
| 6 | 使用文档可用 | 按步骤启动验证 |
| 7 | 验收清单逐条核对 | 需求文档验收清单逐项勾选记录 |

**红线**：
- 任何一项缺证据 → REWORK（指出具体缺口）；
- **以"代码写完"判 Completed 是违规**——必须走完上表七项。

## Review-FAIL-Repair 循环（可选验证）

若配置了 Reviewer 环节，允许故意保留一个可修复问题验证修复链路：

```text
Review 发现问题 → FAIL
→ 指出具体缺陷（如：缺空标题校验）
→ Repair（补校验）
→ Re-Review → PASS
```

修复循环不计为阶段失败，但**最终必须以 PASS 收尾**。
