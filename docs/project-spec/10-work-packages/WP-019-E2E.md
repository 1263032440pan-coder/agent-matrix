## 场景 H：二态自动化模式

### FULL_AUTO

- [ ] Task READY 后自动调度。
- [ ] 普通/高风险不会触发隐式半自动等待。
- [ ] Gate FAIL 可自动进入 Rework / Replan。
- [ ] 缺客户私有信息时使用 NEED_USER_INPUT，而不是创建人工推进节点。

### MANUAL

- [ ] Task READY 后创建 ManualAction。
- [ ] 未确认不得 Dispatch。
- [ ] Apply Replan / Final Delivery 需要人工触发。

### Schema

- [ ] API 拒绝除 FULL_AUTO / MANUAL 之外的自动化模式。

## 场景 J：Existing-Method-First 三档资料完整度

### J1 用户已有 AI-Ready 方法

- [ ] Method Readiness = READY。
- [ ] 基本不创建 Project Method Research。
- [ ] Playbook 保留用户 Procedure Provenance。

### J2 用户资料很多，但 AI 不可直接执行

### J3 Zero-Method Fallback

- [ ] Method Assets 接近 0 时触发 Project Method Research。
- [ ] 仍可形成 Playbook / Task Graph。

## 场景 L：External Skill Package Runtime

前提：Project Runtime 本身不预装任何具体领域 Skill。

### L1 空 Registry

```text
Skill Registry = EMPTY
```

验证：

- [ ] Project 可创建、理解、规划。
- [ ] Optional Skill Task 可继续执行。
- [ ] 不出现“缺某个写死 Skill ID 导致系统无法启动”。

### L2 用户导入测试 Skill Package

测试使用 `40-testing` 中构造的 Mock Skill Fixture，而不是产品内置真实业务 Skill。

流程：

```text
User-supplied Mock Skill ZIP
→ Importer
→ Validator
→ Registry
→ Project Binding
→ Skill Resolver
→ Skill Loader
→ Worker Work Package
→ Worker Result
→ Gate
```

验证：

- [ ] 合法 Skill 可导入并启用。
- [ ] 非法路径/Schema/可执行文件包被拒绝。
- [ ] Binding 固定明确版本。
- [ ] Resolver 不依赖具体领域 Skill ID。
- [ ] Loader 只加载当前 Skill 必要资源。
- [ ] Worker Result 可追踪 skill_id/version/hash。
- [ ] Skill Result 不能直接把 Task 变成 ACCEPTED。

### L3 Version Pin

```text
Project P1 -> mock-skill@1.0.0
Registry 新增 mock-skill@1.1.0
```

验证：

```text
P1 仍使用 1.0.0
```

直到显式修改 Binding。
