# 03 核心领域模型

## Project / Task 状态机规范

> 本章节是 `ProjectStatus` 与 `TaskStatus` 的唯一事实源（Single Source of Truth）。
> 其他全局文档、Work Package、API、Gate、Scheduler 和测试只能引用本章节，不得另行定义第二套状态枚举或合法转移表。

### 1. TaskStatus

```text
CREATED
READY
RUNNING
EXECUTION_DONE
REWORK
BLOCKED
FAILED
ACCEPTED
CANCELLED
```

状态语义：

| 状态 | 语义 |
|---|---|
| `CREATED` | Task 已进入 Task Graph，但尚未满足可执行前置条件 |
| `READY` | 所有 HARD Dependency 已 `ACCEPTED`，且任务本身已具备被 Scheduler 调度的逻辑条件；资源是否足够由 Resource Governor 决定 |
| `RUNNING` | 已由 Scheduler 分派，Worker 正在执行 |
| `EXECUTION_DONE` | Worker 已提交执行结果；仅表示“执行结束”，尚未通过 Gate |
| `REWORK` | Gate FAIL 或失败分析后需要返工，等待重新进入 READY |
| `BLOCKED` | 当前任务因未解决的外部输入、依赖或问题无法继续；当前 Worker 执行应视为已停止/释放 |
| `FAILED` | 本次任务执行异常结束，需要重试或返工 |
| `ACCEPTED` | Gate PASS，任务成果被 Project Runtime 正式接受 |
| `CANCELLED` | 任务被明确取消，不再继续执行 |

### 2. TaskStatus 合法转移表

| From | Allowed To | 典型触发原因 |
|---|---|---|
| `CREATED` | `READY` | 前置条件满足 |
| `CREATED` | `BLOCKED` | 发现缺失私有输入或关键前置条件 |
| `CREATED` | `CANCELLED` | 任务被取消 |
| `READY` | `RUNNING` | Scheduler 成功 Dispatch Worker |
| `READY` | `BLOCKED` | 调度前发现非资源类关键阻塞 |
| `READY` | `CANCELLED` | 任务被取消 |
| `RUNNING` | `EXECUTION_DONE` | Worker 返回执行完成结果 |
| `RUNNING` | `BLOCKED` | Worker 报告无法继续且需要外部解除阻塞 |
| `RUNNING` | `FAILED` | Worker/执行过程异常失败 |
| `RUNNING` | `CANCELLED` | 运行中的任务被取消 |
| `EXECUTION_DONE` | `ACCEPTED` | Gate PASS |
| `EXECUTION_DONE` | `REWORK` | Gate FAIL，需要返工 |
| `REWORK` | `READY` | 返工条件准备完毕 |
| `REWORK` | `CANCELLED` | 任务不再继续 |
| `BLOCKED` | `READY` | 阻塞已解除，重新进入调度队列 |
| `BLOCKED` | `CANCELLED` | 阻塞任务被取消 |
| `FAILED` | `READY` | 可直接重试同一 Task Contract，例如瞬时 Worker/环境故障 |
| `FAILED` | `REWORK` | 需要修改方案、输入或产物后再执行 |
| `FAILED` | `CANCELLED` | 失败后终止该 Task |
| `ACCEPTED` | 无 | 正常完成终态 |
| `CANCELLED` | 无 | 取消终态 |

### 3. Task 状态机硬规则

```text
EXECUTION_DONE != ACCEPTED
```

以下转移明确非法，包括但不限于：

```text
CREATED -> RUNNING
CREATED -> ACCEPTED
READY -> ACCEPTED
RUNNING -> ACCEPTED
BLOCKED -> ACCEPTED
FAILED -> ACCEPTED
ACCEPTED -> REWORK
CANCELLED -> READY
```

约束：

1. 只有 `EXECUTION_DONE -> ACCEPTED` 且 Gate PASS 时才能接受任务。
2. HARD Dependency 只有在上游 Task 为 `ACCEPTED` 时才算满足；`EXECUTION_DONE` 不得解锁下游 Task。
3. Resource Governor 返回 `DEFER_RESOURCE` 时不得把 Task 标记 `BLOCKED` 或 `FAILED`；Task 保持 `READY`，等待资源后再次调度。
4. Gate 返回 `BLOCKED` / 等待人工输入时，Task 默认保持 `EXECUTION_DONE`，通过 `GateResult`、`Issue`、`ManualAction` 或 `UserInputRequest` 表达等待原因；不得无理由回退状态。
5. `ACCEPTED` 为不可回退终态。后续新证据或变更需要重新工作时，应创建新的 Task / Task Revision / Superseding Task，而不是把历史 `ACCEPTED` 静默改回 `REWORK`。

### 4. ProjectStatus

Demo V0.1 冻结为：

```text
CREATED
INITIALIZING
ACTIVE
BLOCKED
COMPLETING
COMPLETED
CANCELLED
```

状态语义：

| 状态 | 语义 |
|---|---|
| `CREATED` | Project 记录已创建，但 Bootstrap 尚未开始 |
| `INITIALIZING` | 正在 Create / Import / Resume、State Discovery、基础初始化 |
| `ACTIVE` | 项目处于正常理解、规划、执行、Gate、Replan 等活动阶段 |
| `BLOCKED` | 存在项目级关键阻塞，导致整个项目当前无法继续推进 |
| `COMPLETING` | 正在执行 Delivery Contract、Completion Evidence、Final Gate 等最终完成判定 |
| `COMPLETED` | Delivery Contract 满足、Required Task 已 ACCEPTED、Critical Issue=0、Final Gate PASS，项目正式完成 |
| `CANCELLED` | 项目被明确终止 |

说明：Demo V0.1 **不定义 ProjectStatus=`FAILED`**。单 Task 失败使用 `TaskStatus.FAILED`；运行时异常使用 Issue/Event/Checkpoint 表达。只有当整个项目无法继续推进时进入 `BLOCKED`，由用户/系统修复后恢复 `ACTIVE`，或明确 `CANCELLED`。

### 5. ProjectStatus 合法转移表

| From | Allowed To | 典型触发原因 |
|---|---|---|
| `CREATED` | `INITIALIZING` | 开始 Bootstrap |
| `CREATED` | `CANCELLED` | 初始化前取消 |
| `INITIALIZING` | `ACTIVE` | Bootstrap / State Discovery 完成，可继续推进 |
| `INITIALIZING` | `BLOCKED` | 初始化缺少关键输入或发现项目级阻塞 |
| `INITIALIZING` | `CANCELLED` | 用户终止 |
| `ACTIVE` | `BLOCKED` | 项目级关键阻塞 |
| `ACTIVE` | `COMPLETING` | 满足进入 Final Completion Check 的前置条件 |
| `ACTIVE` | `CANCELLED` | 用户终止 |
| `BLOCKED` | `ACTIVE` | 项目级阻塞解除 |
| `BLOCKED` | `CANCELLED` | 用户终止 |
| `COMPLETING` | `COMPLETED` | Project Completion 公式全部满足 |
| `COMPLETING` | `ACTIVE` | Final Gate / Completion Check 发现需要返工或 Replan |
| `COMPLETING` | `BLOCKED` | 完成判定阶段发现项目级不可继续的缺失输入/阻塞 |
| `COMPLETING` | `CANCELLED` | 用户终止 |
| `COMPLETED` | 无 | 正常完成终态 |
| `CANCELLED` | 无 | 取消终态 |

### 6. 状态修改唯一入口

任何模块均不得直接写 `Project.status` / `Task.status`。所有状态变化必须经过：

```text
Command / Proposal
→ StateTransitionService
→ Transition Validation
→ State Transaction
→ State Mutation
→ Event Persist
→ Commit
```

以下组件只能“提出”状态变化或产生触发条件：

```text
Planner
Scheduler
WorkerRuntimeAdapter
Worker Runtime
Gate
Replanner
Extension / Plugin
UI
```

真正提交状态变化的唯一主体是 Stable Kernel 中的 `StateTransitionService`（或等价 Core State Machine Service）。状态变更与对应 Event 必须处于同一事务边界，避免“状态已改但事件未记录”或反向情况。

### 7. 非法状态转移错误

统一错误码：

```text
INVALID_STATE_TRANSITION
```

错误至少包含：

```text
entity_type
entity_id
from_status
to_status
reason
correlation_id
```

非法状态转移必须：

- 不修改数据库状态；
- 不产生成功状态事件；
- 留下可审计失败记录/日志；
- 向调用方返回确定性错误。
