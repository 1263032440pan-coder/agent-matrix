# 01 系统架构总则

## 核心分区

```text
Project Runtime
├── Stable Kernel
├── Orchestration Engine
├── Extension Runtime
├── Project Memory
├── Project Capability Discovery
├── Dynamic Planner
└── Completion / Delivery
```

## Stable Kernel

不可由插件替换：

```text
Project State
Task Lifecycle
Artifact Lifecycle
Event Bus
Gate Lifecycle
Checkpoint
Transaction
Command Validation
```

## Orchestration Engine

```text
Pipeline Engine
Scheduler
Lifecycle State Machine
```

## Extension Runtime

```text
Plugin Manager
Extension Registry
Provider Registry
Hook Registry
Middleware Registry
Validator Registry
Observer Registry
Permission Manager
```

## 核心原则

1. Plugin Package 与 Extension 分离。
2. 一个 Plugin Package 可以注册多个 Extension。
3. Capability Extension 与 Runtime Extension 必须区分。
4. Event Bus 只能被订阅，不能被插件改写。
5. Project State 只能由 Core Transaction 修改。
6. Runtime Extension 通过 Proposal / Command 影响流程。
7. Extension Point 使用稳定 ID。
8. 多 Extension 顺序通过 priority / before / after 编译。
9. 插件崩溃不能直接导致 Core State 损坏。
10. 未知未来能力优先通过 Extension Runtime 接入，而不是修改核心链路。

## 自动化控制原则

1. 自动化模式只允许 `FULL_AUTO / MANUAL`。
2. `FULL_AUTO` 在既定权限与硬边界内自动推进，不逐风险请示。
3. `MANUAL` 的状态推进动作必须人工触发/确认。
4. `NEED_USER_INPUT` 表示缺信息或凭据，与自动化模式分离。
5. Runtime Extension 不允许引入第三种自动化模式。

## 资源调度原则

1. Planner 表达逻辑依赖和可并行性，不根据机器配置改变 Task Graph。
2. Scheduler + Resource Governor 决定实际并发。
3. 资源不足返回 `DEFER_RESOURCE`，不是 FAIL。
4. FULL_AUTO / MANUAL 与 LOW / STANDARD / HIGH 完全正交。
5. Worker / Plugin 默认支持按需启动和回收。

## V1.9 认知流程演进原则

Stable Kernel 不绑定具体“如何发现项目方法”的流程。

认知层允许从：

```text
Research-first
```

演进到：

```text
Existing-Method-first / Research-on-Gap
```

而不修改：

```text
Project State / Task Graph / Artifact / Event / Gate / Checkpoint / Transaction
```

这属于 Microkernel + AOP / Extension Runtime 的明确设计目标。

## V1.12 Skill Runtime Infrastructure

Skill 内容不属于 Project Runtime 内置业务资产。Project Runtime 只提供 Skill 基础设施。

```text
User / Organization / Plugin
        │
        │ Import Skill Package
        ▼
Project Runtime
├── Skill Package Importer
├── Skill Validator
├── Skill Registry
├── Skill Binding
├── Skill Resolver
└── Skill Loader
        ↓
Worker Runtime / Project Method Intelligence
```

### 边界

1. Project Runtime **不预装任何领域 Skill** 作为启动前提。
2. 初始 `Skill Registry = EMPTY` 必须是合法状态。
3. Project Runtime 不依赖任何具体 Skill ID 才能启动、理解项目、规划或执行无 Skill Task。
4. Skill 内容由用户、组织或 Plugin 后续提供；Runtime 只负责导入、校验、注册、绑定、解析、加载和审计。
5. Skill 不属于 Stable Kernel，也不拥有 Project State / Task State / Task Graph / Event Bus。
6. Skill 是声明式方法资产；可执行代码、Tool、Worker、Provider 仍由 Worker Runtime / Plugin / Extension 提供。
7. Skill Package V0.1 不执行包内任意脚本；发现可执行文件时必须拒绝或标记 INVALID。
8. Skill 可以通过 Plugin 分发，但 Skill 与 Plugin 是不同概念。

### Skill 三层分类

```text
PROJECT_METHOD
TASK_EXECUTION
CAPABILITY
```

- `PROJECT_METHOD`：完整项目方法，参与 Project Playbook 构建。
- `TASK_EXECUTION`：某类 Task 的可复用执行方法，加载给 Worker。
- `CAPABILITY`：某项能力的使用方法；实际能力必须由 Tool / Worker / Plugin 提供。

### Runtime 选择原则

```text
Explicit Binding
→ Explicit Reference / Preference
→ Metadata Exact Match
→ Generic Fallback
→ NONE / NOT_FOUND
```

规则可确定时不得调用 LLM。只有多个候选满足全部硬条件且优先级完全相同时，才允许 LLM 辅助 tie-break。

### D17.5 增量原则

当前 D01～D17 已完成并冻结。Skill Runtime 作为 D18 前的增量能力接入：

```text
D17A Skill Registry
→ D17B Skill Package Import + Validation
→ D17C Skill Resolver + Project Binding
→ D17D Skill Loader + Worker Execution Integration
→ D18 E2E
```

不得为了引入 Skill Runtime 重做 D01～D17 或重构 Stable Kernel。
