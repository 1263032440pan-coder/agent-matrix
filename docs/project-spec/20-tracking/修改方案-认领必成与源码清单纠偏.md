# 修改方案：认领必成与源码清单纠偏

> 版本：2026-10-29  
> 前置：交付清单 AI 认领与收口对齐（SYS-106～117）；计划期过载拆分（SYS-118～126）  
> 状态：已实现（SYS-127～132，2026-10-29）  
> 触发实测：清单「项目源码」被抽成 `ext:[.zip]` → 认领标为 `package` → 挂到偏前的「Worker执行」→ 顺序门失败 → **删光任务图** → Dashboard 空图  
> 原则：  
> 1. **认领步骤必须成功**：不允许以「删图 / INVALID 甩给用户重试」作为认领的正常结局。  
> 2. **从清单真源纠偏**：禁止把「项目源码」类项默认抽成单独 `.zip` 包（方案 3）。  
> 3. **硬门公式不关**：SYS-109/110 仍生效；过不了就返工，最终走确定性兜底，兜底必须构造成能过硬门。  
> 4. **与过载拆分正交**：认领（含兜底）成功后再跑令牌负荷 / 拆分；拆分失败语义不变。

---

## 一、问题定性

| 层 | 发生了什么 | 后果 |
|--|--|--|
| 清单抽取 | 「项目源码」`match.ext = [.zip]`（并带 readme 前缀） | 真源把「源码」写成了压缩包 |
| 类别标注 | LLM（或启发）标成 `package` | 触发 package 顺序门 |
| 分配 | 挂到拓扑偏前的 `Worker执行` | `package` 主责早于其它非 package 主责 |
| 失败策略（现网） | `DELIVERY_ASSIGNMENT_INVALID` + **DELETE 全部非 ACCEPTED 任务** | 用户看到空 Task Graph，误以为没生成计划 |

根因不是「顺序门算错」，而是：**错误真源 + 认领允许失败并毁图**。

不可行路径：关掉 package 顺序门；认领失败仍 `READY`；要求用户改 skill。

可行路径：纠清单 → 认领 LLM 仍试 → 硬门不过则确定性兜底必过 → 保留任务图 → 再进入过载拆分。

---

## 二、目标

1. 「项目源码 / 源代码 / 代码」类清单项**不得**仅以 `.zip` 作为源码表达；`.zip` 留给明确的发行/安装/发布包。  
2. 认领阶段在任务图与清单均存在时：**必须**产出通过 SYS-109/110 的全覆盖单一主责表，并写入 `deliverable_ids`。  
3. 认领失败路径**禁止**删除任务图；认领阶段**禁止**因「模型分派不佳」置 `INVALID`。  
4. `INVALID` 仅保留给不可修复结构（无任务、无清单、拓扑无法安置 verification/package 等极端情况，须有明确 error_code）。  
5. Dashboard / toast：兜底成功可轻提示；不再出现「空图 + 像没规划」的体验。

---

## 三、方案总览

```
材料 → 抽清单
         ├─ 提示：源码≠zip；发行包才 zip
         └─ validate/normalize：源码类仅 zip → 拒收或改写为代码 ext
  → 冻结核验脚本
  → 建任务图（plan_status=ASSIGNING）
  → 认领
         ├─ AI 标注 + 分次分配 + 硬门（返工 ≤3，已有）
         ├─ 仍不过 → ★ 确定性兜底分配（必过 109/110）
         └─ 写 deliverable_ids（禁止删任务）
  → 过载拆分（已有 SYS-118～126）
  → plan_status=READY
```

对既有认领方案 §4.5「失败删除本轮新建任务」的修订：**删除该失败毁图策略**；改为「认领必成（LLM 或兜底）」。

## 四、清单真源纠偏（方案 3）

### 4.1 抽取提示

在 `extract_manifest_from_materials` 提示中明确：

- **代码 / 项目源码 / 源代码**：`ext` 须含语言或文本源码后缀（如 `.py` `.ts` `.js` `.go` `.java` `.rs` `.md` 等约定集合），可同时 `any_name_prefix:["readme"]`；**禁止**把整项 `ext` 写成仅 `[".zip"]`。  
- **发行包 / 安装包 / 发布包 / 交付压缩包**：才允许 `.zip` / `.tar.gz` 等为主要 `ext`。  
- 若材料只要「可运行源码」而非「打好的 zip」，不得发明 zip 交付项替代源码项。

### 4.2 Runtime 归一化 / 硬约束

在 `validate_manifest`（或紧随其后的 normalize）增加确定性规则：

**判定「源码类项」**（名称或 `name_contains` 命中，不特化某一语言产品）：

- 名称或针含：`源码|源代码|代码|code|source`（大小写不敏感）  
- 且名称**不**命中：`安装包|发行包|发布包|release|installer|安装程序`

**规则：**

| 条件 | 动作 |
|--|--|
| 源码类且 `ext` 仅含压缩类（`.zip` / `.tar` / `.tar.gz` / `.tgz` / `.7z` / `.rar`） | **改写**：将 `ext` 替换为默认源码后缀集合（V0.1：`[.py, .md, .toml, .json]`，可配置常量）；保留 `any_name_prefix` / `name_contains` / `min_count`；`source` 元数据记 `coerced_from_archive: true` |
| 源码类且 `ext` 同时含压缩类与代码类 | **去掉**压缩类后缀，保留代码类 |
| 非源码类的明确发行包 | 不改写 |

改写后必须再过现有 match 合法性（至少有 `ext` 或 `name_contains`）。  
改写须打日志 / 可选事件，便于观测「清单被 Runtime 纠偏」。

### 4.3 与类别标注

真源纠偏后，标注阶段更易标成 `source`。仍建议在 `annotate_categories` 后保留轻量纠偏（可选，非本方案阻塞）：源码类名称 + 已是代码 `ext` → 若仍标 `package` 则强制 `source`（`reason=runtime_coerce`）。

## 五、认领必成

### 5.1 删除「失败毁图」

`assign_in_session` 在 `DeliveryAssignmentError` 时：

- **删除** `DELETE FROM task` / 清依赖的逻辑。  
- 认领路径上，模型分派不佳**不得**再抛到 API 变成「规划 422 + 空图」。

修订认领方案 §4.5 失败行：

| 项 | 旧 | 新 |
|--|--|--|
| 失败 | 删本轮任务或 INVALID + toast | LLM 返工 → 确定性兜底 → 仍写 ids；仅不可修复结构才 INVALID（且**不删图**，若尚无图则保持无图） |

### 5.2 LLM 路径（保持）

现有：标注 → 分次分配 → 硬门 → 返工 ≤3 → 可选复核。不变。

### 5.3 确定性兜底分配（新，必过硬门）

当 LLM 路径硬门仍失败（或 `llm is None` 的测试/降级路径）时，调用 `deterministic_assign(...)`：

输入：清单 + 类别（纠偏后）+ 任务 + 角色 + 拓扑序 + 冻结的 ACCEPTED 认领。  
输出：`id → task_key`，且 `validate_assignment_hard_gate` 必须为空 problems。

**安置规则（V0.1）：**

| 类别 | 挂到 |
|--|--|
| `source` | 拓扑序上最后一个 `implement`；若无 implement → 最后一个非 `process`；若仅 process → 最后一节点 |
| `document` / `other` | 负载最低且不破坏后续 package/verification 约束的节点；平局取拓扑更靠后 |
| `verification` | 最后一个 `verify`；若无 → 全图最后一节点；写入后须满足「不早于任一 implement」——若仍早，则改为全图最后一节点 |
| `package` | 优先最后一个 `deliver`；否则全图最后一节点（保证 ≥ 所有非 package 主责） |

算法顺序建议：先落冻结项 → 再落 `source` → `document`/`other` → `verification` → `package`（package 最后落，天然满足「不早于打包对象」）。

落完后跑 SYS-109/110；若仍有 problems（理论上仅极端图），允许一次「全部剩余/冲突项挤到 topo 最后节点」的塌缩修复；再失败才视为不可修复。

### 5.4 不可修复结构（唯一可 INVALID）

仅当例如：

- 无任务节点却有非空清单；或  
- 清单校验本身失败（上游应已挡住）；或  
- 塌缩修复后硬门仍非空  

才 `plan_status=INVALID` + 422 + toast，且**仍不删**已有任务（若有）。error_code 可沿用 `DELIVERY_ASSIGNMENT_INVALID` 或细分 `DELIVERY_ASSIGNMENT_UNRECOVERABLE`。

### 5.5 观测

- 事件 / 返回体：`assignment_mode: "llm" | "deterministic_fallback"`  
- 兜底时 toast 可选：`交付认领已使用确定性兜底`（不挡 READY）  
- Dashboard：`INVALID` 时展示 problems；有任务时不得因认领失败被清空

## 六、与过载拆分 / 执行

- 认领（含兜底）写入 ids 后，照常 `seed` 令牌 → 过载拆分 → `READY`。  
- 拆分失败仍按过载方案：不落拆分图、可 INVALID（与认领必成分开）。  
- `_TOOL_ROUNDS`、Grace、收口扫项目根：不变。

---

## 七、验收

1. 合成清单：名称「项目源码」+ 模型输出仅 `.zip` → 归一化后 `ext` 为代码集合（或等价非纯压缩），带 `coerced_from_archive` 可观测。  
2. 明确「发行包.zip」项不被改写成源码后缀。  
3. 人为让 LLM 分配恒失败（注入坏 llm_fn）→ 仍 `READY`（或进入过载拆分），`deliverable_ids` 全覆盖，硬门 problems 空，**任务数不减少**。  
4. 回归：正常 LLM 认领仍可走 LLM 路径；兜底不抢先于硬门已通过的结果。  
5. 不再出现：认领失败后 `tasks=0` 且 UI 空图。  
6. package / verification 顺序门单测：兜底产物必须通过。

---

## 八、实现顺序

1. `validate_manifest` / normalize：源码类禁纯压缩 ext + 改写常量与单测。  
2. 抽取提示补充（方案 3）。  
3. `deterministic_assign` + 硬门黄金用例（含 package 在链尾）。  
4. `assign_in_session`：去掉删任务；LLM 失败后兜底；返回 `assignment_mode`。  
5. API / Dashboard / toast 观测字段。  
6. 更新认领方案 §4.5 与 RTM；端到端重跑原失败材料。

## 十一、已知残余风险

| 风险 | 说明 |
|--|--|
| 默认源码后缀集合不准 | V0.1 用通用集合；材料若是纯前端/纯 Go，可能多验一些后缀——Stop/收口按 match，可后续按画像收窄 |
| 兜底边界粗 | 不保证模块语义最优，只保证覆盖与顺序；可接受 |
| 清单项本名就叫「源码安装包」 | 排除词命中发行包则不改写；边界依赖命名 |
| 过载拆分仍可能 INVALID | 与认领必成分开；用户仍可能在拆分段看到失败，但任务图应还在 |
