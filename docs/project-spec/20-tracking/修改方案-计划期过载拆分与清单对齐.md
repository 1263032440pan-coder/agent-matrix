# 修改方案：计划期过载拆分与清单对齐

> 版本：2026-10-28（逻辑复查修订）  
> 前置：交付清单 AI 认领与收口对齐（SYS-106～117）；工具预算 32 + Grace（每节点 32 轮、Grace 后 Stop 失败不返工）  
> 状态：待实现  
> 原则：  
> 1. **与用户 skill 正交**——不改、不依赖用户技能包 stages 粗细；skill 细只是锦上添花。  
> 2. **不特化产物类型**（PPT/某语言仅为现象举例）。令牌按 `match` 字段展开，不按语言或文件类型写死分支。  
> 3. **负荷只计可拆走的义务令牌**；LLM 只提案怎么划分，Runtime 硬门决定是否接纳；模型失败则用确定性装箱兜底。  
> 4. **拆节点不改清单集合**；验收真源仍是 `delivery_manifest`；令牌是节点上的执行义务，不是新的清单 id。拆完必须再过认领全覆盖硬门。  
> 5. **内存图通过全部硬门后一次落库**。片级通过不写数据库。

---

## 一、问题定性

实测：清单「项目源码」整项挂到单一「Worker执行」节点 → 32 轮工具用尽 → Grace → Stop 因缺 `readme*` 失败 → FAILED。  
Grace 后不再给工具返工（预算方案既定），单次执行无法靠「再多轮」硬扛。

根因不是「32 太小」 alone，而是**规划粒度与工具预算不匹配**：

| 能力 | 现状 |
|--|--|
| 用户 skill stages | 不可控；常把实现收成一粗阶段 |
| 流程抽取 | 提示偏「3–10 节点、勿拆太细」 |
| 认领 | 大包 id 可整挂单节点 |
| Worker | 每节点 32 轮（同一常量，不按节点类型加码）；过载节点打满即 Grace→Stop→FAILED |

**不可行路径**：改用户 skill；按节点类型无限加 `_TOOL_ROUNDS`；执行中途动态插节点（打穿 Stable Kernel）；把「实现类」做成拆不走的固定加分（子节点原样继承后永远过不了硬门）。

**可行路径**：计划期把可拆义务展开成令牌 → 负荷过阈则拆节点并划分令牌 → 每个子节点用自己的 32 轮完成自己的令牌 → 清单 id 仍单一主责，收口仍按清单 id 扫项目根。

---

## 二、目标

1. Runtime 能**量化**节点执行负荷（只看计划产物上的义务令牌，不看 skill 好不好）。  
2. `load ≥ LOAD_MAX` 的节点必须在规划期被拆成子任务；子任务负荷严格低于阈值。常量必须保证：只要过载，算术上就一定能划分到阈值以下。  
3. 拆完后：\(\cup\) 节点.`deliverable_ids` == 清单全部 id，且单一主责（复用 SYS-109 硬门）。令牌多重集合守恒。  
4. 令牌 Stop 验本节点义务（本任务目录）；清单 Stop 与项目收口验清单 id（项目根）。齐套后收口零无故补建。  
5. 与 skill 正交；不引入第三种自动化模式；不按扩展名写死拆分规则。  
6. `_TOOL_ROUNDS` 仍为每节点 32；本方案不引入按节点例外轮次。

## 三、方案总览

```
材料 +（可选）skill 骨架
  → 抽清单 + 冻结核验脚本          【已有】
  → 建任务图 + AI 认领 → 硬门      【已有 SYS-106～112】
  → ★ 展开义务令牌，计算各节点 load
       ├─ 皆 < LOAD_MAX → plan_status=READY
       └─ 存在过载 → 内存图上逐节点拆分
            ├─ 模型提案（失败则该节点确定性装箱）
            ├─ 片级硬门 + 整图 SYS-109/110 + 全员 load < LOAD_MAX
            ├─ 失败 → INVALID + toast（内存图丢弃，不落库）
            └─ 通过 → 一次短事务改图 → READY
  → 执行：每节点 32 轮 + Grace/Stop
       令牌 Stop 扫本任务目录；清单 Stop 扫项目根
  → 收口：逐 id 扫项目根（不变）
```

插入点：认领硬门通过之后、`plan_status=READY` 之前（`plan_status` 保持 `ASSIGNING`）。  
本阶段**不**再次调用认领模型，**不**触发 SYS-113。  
重规划（SYS-113）在任务集合变化并重新认领之后，**再**整轮跑过载检测。

## 四、负荷量化（确定性）

### 4.0 边界

| 承诺 | 不承诺 |
|--|--|
| 同一计划产物 → 同一组令牌、同一分数；可单测 | 分数 = 真实工具轮次数 |
| 过载时一定能把令牌划分到每个子节点 `load < LOAD_MAX` | 用 LLM 自评复杂度做硬门 |
| 划分后的令牌有 Stop，对应 32 轮有硬义务 | match 很瘦且材料功能点为 0 时，仍能发现「实际要写很多文件」 |

`code_stage` / 实现类 `task_type` 只用于子节点继承和角色校验，**不进入负荷**。合同字符数不进入负荷。清单 id 的主责身份不加分。

### 4.1 义务令牌

对每个非冻结节点，从计划产物展开令牌。`load` = 该节点持有令牌的权重之和。

| 令牌 id | 来源 | 权重 | 划分 |
|--|--|--|--|
| `ext:{deliverable_id}:{extension}` | `match.ext` 的每一项 | 1 | 整枚移走 |
| `prefix:{deliverable_id}:{value}` | `match.any_name_prefix` 的每一项 | 2 | 整枚移走 |
| `name:{deliverable_id}:{value}` | `match.name_contains` 的每一项 | 1 | 整枚移走 |
| `count:{deliverable_id}:{bundle_index}` | `match.min_count`（缺省按 1） | 1 | 按配额拆开 |
| `output:{index}` | `stage_outputs`，最多 `Ocap` 条 | 1 | 整枚移走 |
| `feature:{index}` | 材料功能点粗计数 `P`，最多 `Pcap` 个 | 1 | 整枚移走 |

数量令牌个数 `n = ceil(min_count / FILES_PER_TOKEN)`。第 `i` 枚（从 1 计）配额为 `FILES_PER_TOKEN`，最后一枚配额为 `min_count - (n-1) × FILES_PER_TOKEN`。`min_count=8` → 两枚，配额各 4；`min_count=5` → 配额 4 与 1；`min_count=4` → 一枚，配额 4。

`P` 缺材料或关闭时为 0。必须可测、可关，不是主信号。

单枚令牌权重只有 1 或 2。发布约束（黄金单测）：**任意单枚权重 `< LOAD_MAX`**。

### 4.2 公式与阈值（V0.1 常量）

```
load = Σ weight(token)   # 本节点持有的令牌
触发：load ≥ LOAD_MAX
接纳：每个子节点 load < LOAD_MAX
```

| 常量 | 初值 | 含义 |
|--|--|--|
| `FILES_PER_TOKEN` | 4 | `min_count` 每 4 个文件一枚数量令牌 |
| `Ocap` | 8 | `stage_outputs` 最多展开 8 枚 |
| `Pcap` | 8 | 材料功能点最多展开 8 枚 |
| `LOAD_MAX` | 6 | `load ≥ 6` 必须拆节点 |
| `BIN_CAPACITY` | 5 | 兜底装箱容量，等于 `LOAD_MAX - 1` |

持有清单 id **不加分**。因此「实现类 + 只认领 1 项」不会仅因身份过载。

落地后可以用历史 Grace/Stop 失败回放改 `LOAD_MAX`、`FILES_PER_TOKEN`、`Ocap`、`Pcap`。改参不得破坏「单枚权重 < LOAD_MAX」。

**验算（原失败样本一类）：** `ext` 4 个、`any_name_prefix=readme*`、`min_count=8`、无 stage_outputs、`P=0`。

`load = 4×1 + 2 + ceil(8/4)×1 = 8 ≥ 6`，触发拆分。

| 子节点 | 令牌 | load | 清单 |
|--|--|--|--|
| 实现-数据层 | 4 个 `ext` + `count:1`（配额 4） | 5 | 无 |
| 实现-收口 | `prefix:readme` + `count:2`（配额 4） | 3 | `d1` |

两节点都 `< 6`。`readme*` 与后 4 个文件留在收口节点自己的目录里；扩展名文件与前 4 个文件留在数据层目录里。

对照：只有 `ext:.py`、`readme*`、`min_count=1` 时，`load = 1+2+1 = 4 < 6`，**不拆**。match 写不出体积、材料功能点又是 0 的大包，V0.1 不假装能拆开（见 §八）。

实现：`expand_obligation_tokens(...) -> list[Token]` 与 `compute_task_load(...) -> int` 纯函数。  
`expand_obligation_tokens` 只用于拆分前的原节点。子节点的 `load` **只等于划分给它的那些令牌**，不得因为子节点仍主责某个 id，就按该 id 的整份 `match` 再展开一遍。

### 4.3 实现类字段（不参与打分）

子节点从被替换节点复制 `code_stage`、`task_type`。  
禁止用扩展名或框架名推断 `code_stage`。

## 五、过载拆分

### 5.1 触发

认领硬门通过后，只对 **非 `ACCEPTED` 且非 `RUNNING`** 的节点展开令牌并算 `load`。  
存在 `load ≥ LOAD_MAX` → 进入拆分，`plan_status` 保持 `ASSIGNING`。  
`ACCEPTED` / `RUNNING` 冻结：不拆、不改边，也不纳入「全员 `< LOAD_MAX`」的失败条件。首次规划没有这两类节点，因此首次规划要求每个新节点 `load < LOAD_MAX`。

### 5.2 AI 提案：逐节点拆 + 全局快照（禁止一次吐整图）

**禁止**一次 LLM 调用输出「所有过载节点的拆解表」。  
**必须**：一次只拆一个过载节点；每轮带上全局只读快照。  
V0.1 子任务只排成**一条链**。运行时接线，不采纳模型自造的跨图依赖。

| 常量 | 初值 | 含义 |
|--|--|--|
| `DECOMPOSE_NODE_RETRY` | 2 | 同一节点模型提案失败次数（含 JSON 与片级硬门） |
| `DECOMPOSE_SPLIT_BUDGET` | 16 | 一次规划中允许替换的节点数，含新拆出又过载的节点 |

#### 5.2.1 编排顺序

```
Q = 队列(拓扑序上 load≥LOAD_MAX 的可拆节点)   # 先上游后下游
G = 当前任务图的内存副本（含认领与令牌）
split_count = 0

while Q 非空 且 split_count < DECOMPOSE_SPLIT_BUDGET:
    T = Q 弹出
    1. 组装 T 的详情 + 全局快照
    2. LLM 只输出 T 的 replace/subs JSON（同一节点最多 DECOMPOSE_NODE_RETRY 次）
    3. 片级校验失败 → 重试本节点；重试用尽 → 对 T 做一次确定性装箱（§5.2.5）
    4. 片级通过 → 只在内存图 G 中用 subs 替换 T
    5. 重算 G 上可拆节点的 load；新过载节点追加进 Q
    split_count += 1

预算用尽仍有过载 → 对剩余过载节点各做一次确定性装箱（不再请模型）
然后对 G：SYS-109/110 + 每个可拆节点 load < LOAD_MAX
通过 → 一次短事务提交 G
失败 → 丢弃 G，PLAN_DECOMPOSE_INVALID
```

与认领分片同构的是「逐片产出 → 片级拒收 → 合并」。不同点：合并先发生在内存，数据库只在整闸通过后写一次。

#### 5.2.2 每轮输入：当前节点 + 全局快照

| 块 | 内容 | 作用 |
|--|--|--|
| **当前节点（必拆）** | name / task_type / contract 摘要、`deliverable_ids`、令牌全表（id、权重、配额）、`load`、直接上下游 | 模型只划分这一处 |
| **全局任务表（只读）** | 全部 `task_key`、status、load、是否已拆过、拓扑序、role | 避免重名 |
| **已拆结果摘要** | 本轮已替换的 `旧名 → [子任务名…]` | 后续节点不再引用已删除的旧名 |
| **清单总表（只读）** | 全部 id + name + category | 不发明新 id |
| **剩余过载队列** | 还未拆的 `task_key` | 避免抢同一批令牌 |
| **接线约束** | 链、id 主责必须位于其令牌节点之后、`source` 主责必须是 `implement` | 减少必拒提案 |
| **材料摘要** | 截取 | 语义边界参考 |

全局块一律标注 **「只读：禁止在本轮输出中修改其他节点」**。

#### 5.2.3 每轮输出（仅一个 replace）

规范字段是 `obligation_tokens`、`deliverable_ids`、`role`、`contract`。`stage_outputs` 由运行时按该子节点分到的 `output:*` 令牌回写。`depends_on` 若出现且与 §5.2.6 的链不一致，片级拒收。

```json
{
  "replace": "Worker执行",
  "subs": [
    {
      "task_key": "实现-数据层",
      "role": "implement",
      "deliverable_ids": [],
      "obligation_tokens": [
        "ext:d1:.py", "ext:d1:.md", "ext:d1:.toml", "ext:d1:.json",
        "count:d1:1"
      ],
      "contract": "在本任务目录交出上述扩展名文件，数量配额 4。"
    },
    {
      "task_key": "实现-收口",
      "role": "implement",
      "deliverable_ids": ["d1"],
      "obligation_tokens": ["prefix:d1:readme", "count:d1:2"],
      "contract": "在本任务目录交出 readme* 与剩余数量配额 4。"
    }
  ]
}
```

上例负荷为 5 与 3，均 `< 6`。

片级校验（只针对 T，不过不改内存图）：

1. `replace` 等于本轮的 `T`；`subs` ≥ 2。  
2. `task_key` 不与 G 中已有名字冲突；`role ∈ {process, implement, verify, deliver}`。  
3. 原挂在 `T` 上的每个清单 id 在 subs 间恰好出现一次；不得出现 T 没有的 id。  
4. 令牌 id 的多重集合与 T 的令牌完全相同。  
5. 每个子节点至少持有一枚令牌，或是某个原 id 的唯一主责。  
6. 每个子节点重算 `load`，严格 `< LOAD_MAX`。  
7. 持有某 id 的子节点，必须排在「持有该 id 令牌」的所有子节点之后（链上的下标更靠后）。  
8. 主责 `source` 类 id 的子节点，`role` 必须是 `implement`。  
9. 按 §5.2.6 预演接线后无环，且 SYS-110 顺序仍成立（verification 不早于任一 implement；package 不早于其打包对象）。  

子节点的 `code_stage`、`task_type` 由运行时从 T 复制，并在提交时写入 SYS-109 使用的角色表。模型不新造这两项。

规则提示（给模型）：把令牌分成若干份，每份负荷 `< LOAD_MAX`；清单 id 可以只留在链尾，但链尾前面的节点必须已经拿走对应令牌，不能只写一句合同就空过。

#### 5.2.4 同会话 vs 多轮独立调用

- **推荐**：同一 chat 多轮，每轮 user 消息附上**最新**内存图快照。  
- 若网关不保会话：每轮把快照全文放入 prompt。  
- **不要**把多个过载节点的 `subs` 塞进一次 response。

#### 5.2.5 确定性装箱兜底

同一节点模型重试用尽，或拆分预算用尽仍有过载节点时，运行时对该节点做一次装箱，不再请模型：

1. 将该节点令牌按权重从大到小装入容量为 `BIN_CAPACITY`（5）的箱子。单枚权重 ≤ 2，故每箱负荷 ≤ 5。  
2. 箱子按产生顺序串成链，`subs` 个数 = 箱子个数（至少 2；若只有 1 箱却已过载，说明单枚权重破坏了发布约束，直接失败）。  
3. 原节点的全部 `deliverable_ids` 放在最后一箱。id 不加分，最后一箱负荷仍 ≤ 5。  
4. `role`、`code_stage`、`task_type` 复制原节点。原节点若主责 `source`，复制后的 `role` 保持 `implement`。  
5. 走与模型提案相同的片级校验和 §5.2.6 接线。

兜底只保证结构、覆盖和负荷，不保证模块边界好看。

#### 5.2.6 接线（唯一规则）

运行时覆盖模型的跨图依赖，V0.1 不支持把一个节点拆成并行分支：

1. 原前驱 → 链上第一个子节点。  
2. 子节点按 `subs` 数组顺序前后相接。  
3. 链上最后一个子节点 → 原后继。  
4. 插入后重算拓扑。若某个 verification / package 主责早于新出现的 implement 子节点，则从链尾向该主责加一条边。原图已通过 SYS-110 时，该主责不是原节点的祖先，加边不成环。成环则本片失败。

模型若提交 `depends_on` 且与上述结果不一致，片级拒收。不提交则由运行时接线。

### 5.3 整闸与落库

内存图 G 同时满足以下条件才写数据库：

1. 每个发生过的替换都已通过 §5.2.3 片级校验。  
2. 清单集合不变：不得增删清单 id。  
3. 未参与本次替换的节点，其认领与令牌保持不变。  
4. 每个可拆节点 `load < LOAD_MAX`。冻结的 `ACCEPTED` / `RUNNING` 不参与本条。  
5. 全图重跑 **SYS-109/110**（全覆盖、单一主责、一致性、顺序）。角色表使用子节点提交稿里的 `role`。  
6. 依赖无环。

通过：一次短事务中删除被替换节点、插入子节点、写入依赖、`deliverable_ids`、令牌、角色与继承来的 `code_stage` / `task_type`，然后 `plan_status=READY`。  
失败：丢弃内存图，不改已落库的任务图。`PLAN_DECOMPOSE_INVALID`（或复用扩展码）422 + 事件 + toast，`plan_status=INVALID`。

模型提案失败但兜底通过整闸的，仍然 `READY`。`INVALID` 只用于兜底之后仍丢 id、成环、角色不一致或 SYS-109/110 不通过。

**禁止**：硬门失败仍 READY；把过载节点的 id 或令牌弄丢；片级一通过就落库；执行期临时插节点；拆分过程中再次调用认领模型或进入 SYS-113。

### 5.4 与 skill / 抽取提示

- **不修改用户 skill 包。**  
- 可选（非本方案阻塞）：弱化 Runtime 侧 `llm_extractor`「勿拆太细」对实现类的限制——仅辅助，**主保障仍是令牌闸**。

## 六、清单对齐与验收语义

### 6.1 两层执行验收 + 收口

| 层 | 范围 | 扫哪里 |
|--|--|--|
| 令牌 Stop | 本节点令牌（见 §6.2） | 本任务目录 `data/tasks/{project_id}/{task_id}` |
| 清单 Stop | 本节点 `deliverable_ids`，跑冻结脚本 | 项目根 `data/tasks/{project_id}` |
| 项目收口 | 清单全部 id | 项目根（现网） |

id 可以仍只挂在一个子节点上。变小的是令牌集合，不是「把一个大包 match 拆成多个清单 id」。  
持有 id 的节点用自己的 32 轮完成自己留下的令牌，再做一次整包复核。整包复核看得到上游任务目录里的文件。

无令牌且无 `deliverable_ids` 的节点在规划硬门就被拒，不会进入执行。

### 6.2 令牌 Stop 怎么判

在本任务目录内，本节点令牌的合取：

- 持有的 `ext`：目录中须出现这些扩展名的文件。节点同时持有数量令牌时，计入配额的文件必须落在这些扩展名内。节点持有数量令牌但没有 `ext` 令牌时，扩展名过滤沿用原清单项的 `match.ext`。  
- 持有的 `prefix` / `name`：目录中须有满足该项的文件名。  
- 持有的 `count`：目录中满足上述过滤的文件数 ≥ 本节点配额之和。  
- 持有的 `output`：本目录中存在文件名包含该 `stage_outputs` 原文的文件。  
- 持有的 `feature`：本目录中存在文件名包含该功能点原文的文件。`P=0` 时不产生 `feature` 令牌。

不在本节点令牌里的条款，不在这一层检查。因此上游不会因为还没写 `readme*` 而过不了自己的 Stop，收口节点也不会因为上游扩展名文件不在自己目录里而过不了令牌 Stop。

清单 Stop 仍用冻结脚本按本节点 id 扫项目根。文件留在各自任务目录即可，`rglob` 能看见子目录。不要求把文件拷贝到主责目录。`file_rw` 继续禁闭在本任务目录，本方案不开放跨任务写入。

宽扫只给清单 Stop 和收口。令牌节点看不到兄弟目录，不能靠别人的文件提前收工。id 主责在链上晚于自己分出去的令牌节点，轮到它做清单 Stop 时，上游令牌 Stop 已经通过。

### 6.3 单调性

SYS-114 继续约束冻结脚本：各任务目录分别满足自己的子集，合并到项目根后全量 id 仍须通过。  
数量配额按目录相加；禁止「恰好 N 个」这类非单调规则（现网已禁）。

### 6.4 明确不做

- 拆分时改写 `delivery_manifest` 条目集合。  
- 以 Artifacts 数量替代覆盖门。  
- 为抬负荷给单节点加无限工具轮次。  
- 依赖用户改 skill。  
- 用合同篇幅、`code_stage` 固定加分触发拆分。  
- 要求主责节点把兄弟目录中的文件汇聚到自己目录。

## 八、已知残余风险

| 风险 | 说明 |
|--|--|
| match 很瘦 | 只有少量 `ext` / 一个前缀 / `min_count=1`，且 `P=0` 时，负荷可以 `< 6`。实际要写的文件远多于此的大包，V0.1 不拆。不靠「实现类 +4」硬触发 |
| 列表封顶 | `stage_outputs` 超过 `Ocap`、功能点超过 `Pcap` 的部分不产生令牌 |
| 兜底边界粗 | 装箱按令牌顺序切，不保证模块语义；硬门只守覆盖、负荷和拓扑 |
| 主责不能改兄弟目录 | 清单 Stop 失败时，主责只能在自己的目录里补文件。上游若写出脚本不接受、又删不掉的文件，主责补文件不一定能抵消。SYS-114 已禁止非单调脚本，用来收窄这类情况 |
| 冻结节点 | 重规划时 `RUNNING` / `ACCEPTED` 即使负荷偏高也不拆 |

## 九、验收

1. 令牌负荷 `≥ 6` 的合成节点 → 规划产出 ≥2 个子任务，令牌多重集合不变，每个子任务 `load < 6`。§4.2 的 8 分样本拆成 5 与 3。  
2. 单枚令牌权重 `< LOAD_MAX` 的常量约束有黄金单测。`code_stage` 与合同长度不改变 `load`。  
3. 拆后 \(\cup\) 认领 == 清单全部 id；人为弄丢原节点的一个 id 或一枚令牌 → 硬门拒收。无令牌且无 id 的子节点拒收。  
4. 粗单阶段 skill 不参与打分。同一份 §4.2 清单，skill 只有一段时仍然拆分。负荷 `< 6` 的计划不拆，行为与现网一致。  
5. 模型连续失败 2 次 → 确定性装箱后仍 `READY`（在 SYS-109/110 本来就能通过的图上）。兜底后仍丢 id → `INVALID`，且数据库中的任务图与拆分前相同。  
6. 多节点全绿齐套 → 收口零补建；缺一文件 → 仅一 id 补建且有边。  
7. 令牌节点只扫本任务目录：兄弟目录里已有文件不能让它的令牌 Stop 通过。id 主责的清单 Stop 扫项目根，能看见上游任务目录中的文件。  
8. `_TOOL_ROUNDS` 仍为每节点 32；本方案不引入按节点例外轮次。  
9. 拆分阶段不调用认领模型，也不进入 SYS-113。SYS-113 重新认领完成之后，过载检测会再跑一轮。
