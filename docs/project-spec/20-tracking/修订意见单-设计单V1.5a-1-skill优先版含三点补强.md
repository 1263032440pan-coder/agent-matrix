# 修订意见单：设计单 V1.5 → V1.5a-1（skill 优先版 · 含三点补强）

> 版本：V1.5a-1（2026-10-21；V1.5a 初版同日，并入三点开工前补强）
> 对象：《设计单-20号V1.5-代码工程产物三件套》
> 修订动因：
>   ① 用户决策——**行为约束放 skill 层（可换可版本化），代码只做机制不做行为**（opencode 形态对标）
>   ② 检查方核验——原设计单"契约全是文档型"诊断**部分失实**（skill 本就要求源码）
>   ③ 三点开工前补强（用户提出，检查方核验全部属实）：A 执行链触达断链 / B stages 元数据无落点 / C 自觉率判定权归属
> 结论：**三件套框架保留；第①③件按 skill 优先原则重写；第②件原样保留；三点补强全部并入开工前必做项**

---

## 一、诊断修正（先改事实，再谈方案）

**原诊断①**："skill 九阶段的产出物模板就是文档，'项目源码'交付物没被翻译进任务契约"

**核验事实**（检查方解包 skill 原文实证）：`software-project-delivery` v1.0.0 的 SKILL.md **已经要求源码**：
- expected_outputs 含"可本地启动的项目源码"
- 开发实现阶段产出 = "项目源码 + 开发文档（模块清单+启动方式+目录结构说明）"
- 验收 = "按使用文档可本地启动；核心 API 手工调用通过"

**修正后的真实缺口**：
- skill 说了"要源码"，但缺**执行纪律**（多文件组织/逐文件落盘/写完必须跑测试修复失败）——细节在"一句产出声明"里被稀释
- 真正的执行层断链在②（产物只认单 md）与③（无跑通门）——这两条诊断成立

> 设计单文本同步改：第①件表述从"契约全是文档型"改为"**契约缺代码工程执行纪律**"。

---

## 二、修订原则（用户决策）

```
skill 层 = 行为（怎么干：写什么文件/怎么组织/何时跑测试）——可换可版本化可分发
代码层   = 机制（记账/安全/兜底识别）——不写行为模板

opencode 对标：Build agent 的行为细节在 AGENTS.md / agent/*.md / skills/*，
              代码内置的只有工具面与权限矩阵
```

## 三、逐件修订

### 第①件：契约生成 → skill 升级为主，代码兜底为辅

**删除**：`_CODE_DELIVERY_CLAUSE` 代码写死模板 + builder 正则识别为主通道的设计。

**A. skill 升级（主通道）**：`software-project-delivery` 1.0.0 → **1.1.0**，四处改动：

1. **SKILL.md 结构重排（补强 A 的落位）**：frontmatter 之后立即放"**执行纪律总则**"段——九阶段共用纪律，含代码工程四件（多文件组织/每文件独立落盘/README 必附/测试通过才算完成）。**必须进 llm_worker 的 2000 字截取窗口**（检查方实测：执行链触达 skill 的唯一通路是 `llm_worker.py:219` 的 `skill_body[:2000]` 从头截断，"开发实现"排第六阶段，原结构下纪律段必然被裁）。分阶段细则排在纪律总则之后。
2. **开发实现阶段补执行纪律**（分阶段细则层，与总则呼应）：多文件组织（src/ tests/ 子目录）/ 每文件 file_rw 独立落盘 / README 三要素（启动方式/依赖/结构）/ 写完测试必须用 test_runner 跑、失败修复后重跑
3. **测试验证阶段**：验收表述"核心 API 手工调用通过" → "test_runner 自动化通过"
4. **stages 元数据结构化（补强 B 的落位）**：frontmatter 的 stages 从字符串列表扩为结构化：

```yaml
stages:
  - name: 项目理解
    outputs: [项目理解报告]
  - name: 开发实现
    outputs: [入口文件, 功能模块, 测试文件, README]
  - name: 测试验证
    outputs: [测试报告]
  # ... 九阶段逐一定义
```

**B. 代码侧两件小机制**：
- **透传**：skill stages 结构化后，`read_skill_stages` / `importer.py` 支持新旧两种形态（**向后兼容**——旧 zip 字符串列表照导不炸）；`map_nodes_to_stages` 把 outputs 写进 workstream → Planner 提取有结构
- **兜底识别**（原设计降级为 fallback）：skill 未声明而**用户材料明确要求**（正则命中"项目源码/可运行/编译启动"）时置 `code_delivery_required`，叠加**三行最小条款**（多文件+README+测试）——材料约束高于 skill 模板的既有双向规则；不复制 skill 正文

**为什么改现有 skill 不新建**：代码工程是"软件交付方法"的本职不是可选附加技能；九阶段/环节亲和/模板路由全链已接这个 skill，改正文即生效；新 skill 引入共存/选择/冲突复杂度；版本化机制现成（1.0.0→1.1.0，Pin 不漂移）。

### 第②件：产物模型 → 原样保留（无修订）

工作区文件全量登记 Artifact 是**系统记账**，不属模型行为——无 skill 化空间。快照 diff / batch_register / UI 文件树 / Gate 检查（entry+README 存在）设计不变。

### 第③件：反馈环 → skill 纪律驱动 + 代码软提醒观察

**删除**：代码强制 2 次修复循环（独立计数/失败喂回循环结构）。

**改为**：
- **主通道 = skill 纪律**（1.1.0 纪律总则 + 开发阶段纪律）——模型在 12 轮工具循环内自主 test_runner → 读失败 → 修复（opencode-solo 闭环的 prompt 版）
- **代码侧只留软提醒**（一次性）：Worker 收工时检测——任务带 `code_stage` 标记**且**工作区测试文件为零**且**产物含代码文件 → 喂回一次"契约要求测试文件，请补写后重试"；第二次收工放行如实交付
- **自觉率观察（补强 C 的落位——判定权归属，用户 2026-10-21 决策）**：

```
数据收集: 3 个真实项目的 code_stage 任务收工统计
  （测试执行证据存在率 = 有 test_runner 调用事件或测试报告文件的任务 / 全部 code_stage 任务）
报告提交: 开发侧只交数据与事实（每项目一份: 任务数/自觉数/失败模式摘要），
          不做回补建议
判定: 由用户拍板是否启用附录硬门——阈值 70% 仅作参考线不作触发条件
     （样本小，阈值判断本质是产品决策，不留给开发侧裁量）
```

- **硬门草案入附录不删**（原设计第③件的强制循环代码草案文档化保存，用户拍板后随时可启用）
