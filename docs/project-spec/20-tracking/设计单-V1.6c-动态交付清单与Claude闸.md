# 设计单 V1.6c：动态交付清单（路径 1）+ Claude 收工闸

> 版本：V1.6c（2026-10-27）  
> 前置：V1.6 钩子化、V1.6b 收工硬闸（写死三件存在性）  
> 用户决策：方案 **C**（项目总清单 + 任务子集）；实现 **路径 1**（结构化 JSON + 确定性 match）；LLM JSON 不合法 → **桌面 toast 提示用户**。

---

## 一、目标

1. 计划阶段由 AI 从 **skill + 用户材料** 理解产物要求，输出**结构化交付清单**（非代码写死三种）。  
2. 清单落到 **项目级总表**；建任务时把子集挂到节点。  
3. 收工仍用 **Claude Stop 语义**：确定性校验工作区/Artifact → 不过喂回（最多 3 次）→ FAILED。  
4. 抽取结果 **JSON schema 校验失败** 时：不静默吞掉，**API 返回错误码 + 前端 toast** 告知用户。

---

## 二、数据模型

### 2.1 项目级 `delivery_manifest`（新列或 JSON 文件字段）

建议：`Project.delivery_manifest`（Text/JSON，nullable）。

```json
{
  "version": 1,
  "source": "plan_extract",
  "deliverables": [
    {
      "id": "d1",
      "name": "方案PPT",
      "match": {
        "ext": [".pptx"],
        "min_count": 1
      }
    },
    {
      "id": "d2",
      "name": "可运行代码",
      "match": {
        "ext": [".py", ".js", ".ts", ".java"],
        "any_name_prefix": ["readme"],
        "min_count": 1
      }
    }
  ],
  "extracted_at": "ISO-8601"
}
```

`match` 白名单字段（仅允许下列键，防止模型发明无法执行的规则）：

| 字段 | 含义 |
|------|------|
| `ext` | 扩展名列表（小写，含点） |
| `name_contains` | 文件名需包含的任一子串 |
| `any_name_prefix` | 另需至少一文件名以此前缀开头（如 readme）——用于「代码+README」类复合条件 |
| `min_count` | 满足 ext/name_contains 的文件至少几个，默认 1 |

复合语义：`ext`/`name_contains` 定义「主文件」集合；若存在 `any_name_prefix`，还须另有前缀匹配文件（与现 code+README 同构）。

### 2.2 任务级认领

`Task.playbook_ref` JSON 增加：

```json
{
  "deliverable_ids": ["d1"],
  "delivery_tags": []
}
```

- 新路径以 `deliverable_ids` 为准。  
- V1.6b 写死的 `delivery_tags`（ppt/code/test_report）可映射为内置 match **仅作迁移期兼容**，新计划不再依赖写死三件。

## 三、计划阶段流水线

```
材料 + skill《交付基线》
  → LLM 抽取 delivery_manifest（严格 JSON schema）
  → Schema 校验
       ├─ 失败 → 不落库清单；API/事件带错误；UI toast；计划可中止或降级（见 §五）
       └─ 成功 → 写入 Project.delivery_manifest
  → 任务图生成时：模型为节点分配 deliverable_ids（须 ⊆ 总清单 id）
  → 非法 id / 未覆盖的总清单项 → 校验失败同样 toast（分配阶段）
```

抽取 prompt 约束：只输出 JSON；`id` 稳定短串；`match` 只用白名单键。

## 四、校验与 Claude 闸

### 4.1 任务收工（替换 V1.6b 写死规则）

拟终稿且 `deliverable_ids` 非空：

1. 取项目 manifest 中对应项的 `match`  
2. 扫任务工作区（+ 可选项目 Artifact 名）  
3. 不满足 → 注入 `【收工校验未通过——须返工】` + 缺失项名称与 match 说明（最多 **3** 次）  
4. 用尽 → `DeliveryBaselineError` → 任务 **FAILED**

无 `deliverable_ids` 的任务：不拦（与「非交付节点」兼容）。

### 4.2 项目收口

无进行中任务且存在 manifest：

- 对总清单每一项做存在性检查（项目工作区/Artifact 全集）  
- 缺项 → 补建「交付补全-{name}」任务（`deliverable_ids: [该 id]`）并 **submit**  
- 与 V1.6b 收口同构，规则来自 manifest 而非写死三件

## 五、JSON 不合法 → Toast

### 5.1 后端

抽取/解析失败时：

- **不**写入残缺 `delivery_manifest`  
- 返回明确结构，例如：

```json
{
  "ok": false,
  "error_code": "DELIVERY_MANIFEST_INVALID",
  "message": "交付清单 JSON 校验失败：deliverables[1].match 含未知字段 foo"
}
```

- 同步记 `RuntimeEvent`（如 `DELIVERY_MANIFEST_INVALID`），便于历史排查  
- 计划 API（`/plan` 或抽取子步骤）将该错误冒泡到响应（或 SSE/轮询状态字段 `plan_warning`）

**计划是否整单失败（定稿）：**  
JSON 无效 → **本轮计划失败/中止生成任务图**（避免无清单却继续跑）。用户修正材料或重试计划。  
（若用户后续要求「降级继续」，另开变更。）

### 5.2 前端

- 计划/抽取回调或 dashboard 轮询到 `error_code === DELIVERY_MANIFEST_INVALID`（或事件）  
- **Ant Design `message.error` / `notification` toast** 展示 `message` 全文（可读中文）  
- 不静默；可附「重新规划」入口（若已有按钮则复用）

## 六、与 V1.6b 关系

| V1.6b | V1.6c |
|-------|-------|
| `_check_delivery_workspace(tags)` 写死 ppt/code/test_report | `_check_delivery_match(files, match)` + 按 ids 取规则 |
| SOFTWARE_DEV 隐含三件 | 三件仅当抽取结果里出现；**不**再代码写死默认三件（路径 1） |
| 收工 3 次 FAILED | 保留 |

## 七、测试要点

1. Schema 合法 → 落库 manifest  
2. 非法 JSON / 未知 match 键 → API `DELIVERY_MANIFEST_INVALID`，无落库  
3. 任务挂 `d_ppt`、工作区无 pptx → 注入返工；补齐后通过  
4. 3 次仍缺 → FAILED  
5. 收口缺项 → 补建 + submit  
6. 前端：mock 错误码 → toast 出现（组件测或 vitest）
