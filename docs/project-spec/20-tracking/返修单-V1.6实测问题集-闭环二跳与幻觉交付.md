## 二、修改方案（逐项）

### P1 闭环二跳——补建任务收工后再收口（~15 行）

`_delivery_closeout_check` 的触发条件本身没问题（`_auto_advance` 尾部
"无进行中任务"时跑）；**根因**：补建任务 ACCEPTED 走的是 Gate 路径，
Gate PASS 后 `_auto_advance` 确实会被调——但补建任务 7/8 是**同时**
ACCEPTED 的，最后一次 advance 时**两个都已终态**，`if not ids`（无
READY）成立应触发……需实测核实未触发原因（疑：auto-advance 的
MAX_SUBMIT 节流后 `ids` 非空提前 return，或 Gate 后 advance 用的
是当时快照）。

修法：不依赖推测——**Gate PASS 的 `_auto_advance` 尾部无条件补一次
closeout 检查**（幂等，防死循环已由"同名任务存在不再建"护栏兜住——
第二次收口发现还缺只会发事件+标红，不再建任务）。

### P2 幻觉交付拦截——补建任务专属存在性 Gate（~40 行，**拍板点**）

**范围严格限定**：只在 `交付补全-*` 任务（`delivery_tags` 单件）上启用
`BackfillValidator`——查该件**实物存在**（.pptx 文件 / 代码文件+README /
测试报告 md），缺 → FAIL → REWORK（重试一次仍缺 → 终态 FAILED + UI 标红）。

- 这是**记账不是行为**：查"文件在不在"，不判质量——与 FileValidator
  同级同语义，不违背钩子化原则（此前撤掉的 CodeDeliveryValidator 是
  加在**所有** code_stage 任务上的——范围过大，本方案只卡补建任务：
  它的存在意义就是补那件实物）
- 普通 code_stage 任务不 Gate（自查钩子照旧软机制）
- 顺带修 Gate 的"md 声称"幻觉：validator 按扩展名查文件系统，
  不读产物文本——嘴说绕不过去

### P3 补建任务 provision 接线（~10 行）

`_delivery_closeout_check` 建任务时：按 task_type（交付打包→releaser /
开发实现→coder / 测试验证→tester）走既有 `bind_agent` 路由绑定实例——
思维链有主、占用智能体工作流、AgentPanel 实时可见。

### P4 file_rw 嵌套路径（~10 行）

任务8 的 `pom.xml` 落在 `data/tasks/1/8/1/8/`——`__ws_root` 相对路径
拼接把 `1/8/pom.xml` 这类"带任务路径前缀的相对路径"又拼了一层。
修：`_resolve` 前先剥路径中的任务前缀（`{pid}/{tid}/` 开头的相对路径
规整为去掉前缀再拼）+ 单测覆盖该形态。

### P5 runtime 存活监控（~20 行）

- uvicorn 挂 `SIGTERM/except` 钩子写退出日志（死要有遗言）
- 启动脚本（重启三进程的命令）加自动拉起：`while ! curl health; 
  restart; sleep 30` 的看门狗（Windows 计划任务或常驻脚本）
- V1.13 幽灵进程问题的低成本版

### P6 零落码——数据已齐，等你拍板（不在本单实施）

两轮实测：4 code 任务 0 落码 + 2 补建 0 实物。自觉率口径下
"真写码" = 0/6。**硬门上桌条件已满足**——附录草案（强制 test_runner
2 次循环）+ 存在性 Gate（P2 的补建版）双轨，你拍板启用范围。
本单只做 P2（补建任务存在性），主任务的硬门留决策。
