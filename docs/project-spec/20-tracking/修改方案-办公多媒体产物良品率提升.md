# 修改方案：办公/多媒体产物良品率提升（对照开源智能体）

> 版本：2026-11-01（rev3：明确「机制可参考 / 产品形态不照搬」）  
> 前置：V1.6 三件交付；`slide_generator` / `arch_diagram`；完整性静默软放行方案（假 pptx/png）；SYS-093～095 技能沙箱；`20-Worker-Runtime` 已有 Hermes Bot Mode 参照边界  
> 状态：**草案（待拍板）**  
> 问题：代码类产物尚可；`.docx` / 图片 / 表格 / `.pptx` 观感与可用性差；模型常绕过专用工具，用 `write_file`+`shell` 造占位文件。

---

## 〇、本项目定位与对照边界（先读）

本仓库是 **本地单用户桌面应用**：Microkernel + AOP/Extension Runtime；交付靠 **Project State / Task Graph / Gate / Proposal→Transaction**；自动化仅 **FULL_AUTO / MANUAL**。  
对照开源是为了偷 **机制**（写盘路由、反馈回路、专用 ACI），**不是**改成另一类「聊天 Bot / 开发者智能体应用」。

| 对照物形态 | 典型例子 | 与本项目关系 |
|--|--|--|
| **聊天/Bot 产品** | Hermes **Bot Mode**、Messaging Gateway（TG/Discord/…）、Grok Bot 类常驻对话助手 | **产品拓扑不同**：多 Bot 人设、网关会话、Bot↔Bot `message_agent`、远程常驻。本项目是 **项目任务图驱动的 Worker**，不是 Bot roster。规范里已写明：Hermes 人工勾选白名单对 FULL_AUTO 中途派生不适用（见 `20-Worker-Runtime` §派生闸）。 |
| **IDE/CLI 编程助手** | OpenCode、Aider、Claude Code 系 | **会话形态不同**：人对着仓库闲聊改码。我们可抄「write=文本 / 跑测回灌」，不抄其 UX 与权限模型当内核。 |
| **云沙箱 SWE 平台** | OpenHands 全量 Docker/远程 | **部署形态不同**：可远期 ADR 评估「任务执行后端」，不作为 Demo 办公良品前置，更不整平台搬迁。 |
| **办公专用 ACI** | OfficeCLI、DocuLane、docforge、powerpoint-skill | **机制最贴**：结构化生成 + 可选预览。以 Provider/插件接入，服从权限四档与 Stable Kernel。 |

**只参考、不照搬（机制白名单）**

- 可参考：拒 `write` 造二进制；生成后结构/预览反馈；Office 走专用工具或受控 MCP 桥；代码侧「写后轻量诊断 / 真跑测试」思想。  
- 不照搬：Bot Mode / 多平台网关 / 常驻 IM 助手；六后端云沙箱矩阵；完整 LSP 语言服务器集群；把 Core 改成 MCP-first 编排器；用「聊天会话质量」替代 Gate/清单对账。

## 一、现状回答（事实）

### 1.1 常见文件是怎么生成的？

| 类型 | 设计路径 | 实际常走路径 | 结果 |
|--|--|--|--|
| 源码 / md / json | `write_file` / `append_file` | 同左 | LLM 擅长文本 → **相对凑合** |
| 跑测 / 构建 | `test_runner` / `builder` / 白名单 `shell` | 有则用，模型也可能只写不跑 | **有能力但不强制** |
| PPT | **`slide_generator`**（md→python-pptx）或 skill `ppt-master` | 常被 `write_file` 假 `.pptx` + `build.py`+`shell` 替代 | **效果差 / 假文件** |
| 图（原型/流程） | **`arch_diagram`**（mermaid→mmdc→png，否则 `.mmd`） | 常写明文占位 `.png` 或自造脚本 | **差 / 假图** |
| docx / xlsx / 表格 | **无专用工具** | 只能 `write_file` 或 shell 调第三方 | **基本不可用** |

结论：**不全是**「写文件+命令行」。代码路径本就是文本工具；办公/媒体本应走专用 Provider，但约束弱，模型退化成写假后缀。

### 1.2 「沙箱」是不是工具调用？

两套概念，勿混；**开源项目也把二者拆开**：

| 名称 | 是什么 | 怎么进 |
|--|--|--|
| **Skill 安装沙箱**（SYS-093） | 四闸：AST / bwrap 冒烟 / 信任 / hash+venv | **安装 EXECUTION skill 时**，不是 Worker 每轮工具 |
| **Worker 执行面** | `shell` 白名单 + 工作区禁闭；`test_runner`/`builder` | **是工具调用**；Windows≈超时+净化 env |
| **对照：Hermes Terminal Backend** | local / Docker / SSH / Modal / Daytona / Vercel | **沙箱是「终端后端」配置**，file/terminal/`execute_code` 走同一环境；≠「某个叫 sandbox 的工具」 |
| **对照：OpenCode** | 自认 **不提供 OS 沙箱**；`permission` 只是 allow/ask/deny UX；真隔离靠外层容器 / Vercel Sandbox | 与我们「白名单 shell ≠ 隔离」同构 |
| **对照：OpenHands** | 推荐默认 Docker，bash/ipython 在容器内 | 任务级隔离最重的一档 |

因此：你看到的「沙箱有了」，多半是 **skill 安装隔离 + shell/test 受限执行**；模型写代码后**不会自动**进沙箱跑全套测试，除非主动调 `test_runner`/`shell`。这与 OpenCode「权限≠沙箱」、Hermes「后端可换但默认 local」一致——**良品率靠反馈回路，不只靠隔离**。

## 二、为何代码尚可、办公媒体很差

1. **模态不匹配**：LLM 原生输出文本；OOXML/位图是结构化二进制，用 `write_file` 几乎必然假货。  
2. **专用工具弱且可绕过**：`slide_generator` 仅「md→简易版式」；无 docx/xlsx；无「渲染预览→返工」闭环。  
3. **Stop 只验存在性**（完整性方案补结构，仍非观感）。  
4. **激励错位**：占位文件也能过 Gate → 良品率无压力。  
5. **对照缺口**：开源头部在「写后反馈」上明显更重——Hermes **write 后喂 LSP 诊断**；OpenCode **`read` 可把 PNG/PDF 像素送回模型**；办公则走 **MCP/Skill/CLI**，而不是 `write` 造二进制。

## 三、开源智能体对照（扩面）

### 3.1 总表

| 项目 | 产物怎么出 | 沙箱 / 执行面 | 办公·图·表 | 可抄的一招 |
|--|--|--|--|--|
| **OpenCode**（anomalyco） | `write`/`edit`/`patch` 文本；`shell`；Code Mode `execute` 链工具 | **无内置 OS 沙箱**；permission allow/ask/deny；外挂容器/Vercel | 内置 `experimental_image_generate`；Office 靠 **Skill + MCP**（DocuLane / docforge 等） | ① `write` 只服务文本；② **`read` 可多模态回传图/PDF**；③ Office **外挂 MCP，不扩 write** |
| **Hermes（工具/执行面）** | `write_file`/`patch` + `terminal`/`execute_code` | 可插拔终端后端（local…云） | `vision_analyze` / `image_generate`；可读 docx/xlsx | **仅机制**：写后诊断思想、视觉回看、沙箱≠工具名。**不抄** Bot Mode / Gateway（见 §〇） |
| **Hermes Bot / Grok Bot 类** | 常驻对话、多 Bot、IM 网关 | 网关进程 + 远程环境 | 附件随聊发出 | **产品形态对照用**：证明「助手应用 ≠ 本项目」；本方案**零采纳其拓扑** |
| **OpenHands** | bash + ipython（CodeAct） | 默认 Docker 等隔离 | 复杂能力偏 Skill | 代码「真跑」思想；不搬整平台 |
| **Goose**（Block） | MCP-first；Code Mode | 扩展可容器化 | Office = MCP extension | 办公放扩展层；不把 Core 改成 MCP 编排器 |
| **Aider** | 编辑格式 + git | 基本无沙箱 | 不覆盖 Office | lint/test 回灌思想 |
| **OfficeCLI / DocuLane / docforge / ppt skill** | 结构化 create/edit/info；部分渲染预览 | 本地引擎/子进程 | **专攻** OOXML | 与本项目 ACI 最贴；经 Provider/插件接入 |

### 3.2 可迁移共性（机制层，不是产品层）

```
代码良品 ≈ 文本编辑 ACI +（跑测 / 轻量诊断）反馈      → 落入 Worker 工具 + Stop/Gate
办公良品 ≈ 专用编辑 ACI +（结构校验 / 规则预览）反馈  → 落入 slide/arch/docx Provider + 完整性
图片良品 ≈ 专用管线（mermaid/生成器）+ 可选回看         → 落入 arch_diagram，不默认扩散模型
沙箱      ≈ 执行边界（skill 闸 / shell 白名单）          → 不升格为「Bot 云主机矩阵」
```

头部差距在 **反馈回路 + Office 专用面**，不在「谁更像聊天 Bot」或「谁的 shell 更炫」。  
**OpenCode / Hermes 工具层**都不把「`write` 吐 pptx 字节」当正路——这点可直接落进本项目 Write Provider。

### 3.3 对我们现状的定位（在本架构内）

| 维度 | 我们（应保持的骨架） | 缺口（本方案要补） |
|--|--|--|
| 编排 | Task Graph + Gate + FULL_AUTO/MANUAL；非 Bot 会话 | 不改拓扑 |
| 代码写盘 | `write_file` + 可选 `test_runner` | 可选：收工测门、写后轻量诊断（**非**完整 LSP 集群） |
| PPT/图 | 已有 `slide_generator` / `arch_diagram` | **强制路由** + 能力升级；禁绕过 |
| docx/xlsx | 无 | 新 Provider 或受控插件桥（ADR） |
| 视觉回环 | 基本无 | V0 规则预览即可；多模态为可选增强 |
| 沙箱 | skill bwrap + shell 白名单 | 够用则维持；云后端仅远期 ADR，**非本方案主线** |

## 四、目标与原则

**目标（良品率）**

- PPT/图/文档：**真实可打开**比例 ↑；占位假文件 ↓  
- 代码：Stop/Gate 后 **至少跑过约定测试** 的比例 ↑（可选闸）；中期可加「写后诊断」软反馈  
- 软放行 `CONTENT_INTEGRITY_SOFT` 占比随迭代下降（度量）

**原则（对齐 AGENTS.md）**

- 专用工具 = Core/插件 Provider 或 **受控 MCP 桥**；经工具循环；**禁止** DIRECT_STATE_MUTATE。  
- 二进制后缀 **禁止** `write_file` 直接落盘（对齐 OpenCode「write=文本」）。  
- Resource Governor 与自动化模式正交，不混。  
- Demo V0.1 可分阶段，但边界清晰。

## 五、改进方案（分阶段，已按对照修订）

### 阶段 A — 路由强制（快，良品率立竿见影）★优先

1. **`write_file` / `append_file` 拒写二进制后缀**（学 OpenCode：write≠二进制）  
   `.pptx/.docx/.xlsx/.png/.jpg/…` → 明确错误码 + 提示改调 `slide_generator` / `arch_diagram` / 未来 office 工具。  
2. **落地「完整性校验 + 限次 nudge」**（已有草案）——假文件不再静默绿过。  
3. **Prompt / derive**：PPT/图任务白名单默认带齐专用工具；收工自查点名工具名。

验收：明文 placeholder.pptx 在 Stop 返工，而非 ACCEPTED。

### 阶段 B — 专用工具升级 + Office 能力补齐

| 工具 | 升级方向 | 对照来源 |
|--|--|--|
| `slide_generator` | 提纲 JSON/分镜；主题与页类型；返回页数/空页元数据 | powerpoint-skill / DocuLane |
| `arch_diagram` | 保证渲染或明确 `.mmd`+原因；禁占位 png | 同上 ACI |
| **新增** `docx_generator` / `sheet_generator`（V0） | 自研 python-docx/openpyxl **或** 试点嵌入 DocuLane/OfficeCLI/docforge（**ADR**：许可证/体积/Windows） | OpenCode MCP 生态、OfficeCLI |
| 可选 **MCP 桥**（插件） | 不把 30+ Office 工具塞进 Core；VALIDATE/ENRICH 边界 | Goose MCP-first |

### 阶段 C — 视觉 / 结构回环（机制借鉴，落在工具返回值）

1. 生成后 **渲染首页/关键页为 PNG 或 HTML**（`office_preview` 或工具返回值内嵌）——借鉴 OfficeCLI「看见再改」，**不是**上 Hermes 式常驻 vision Bot。  
2. V0：**规则检空**（空白、过小、页数）+ 预览路径写进 tool result。  
3. V1（可选）：预览图多模态回看；费用/隐私另议。  
4. 可选：对真实 docx/xlsx **抽结构摘要**回灌 Worker，便于改内容而非瞎 rewrite。

### 阶段 D — 代码「真跑 + 写后反馈」（在现有 Worker 内增强）

1. 挂 `test_runner` 的节点：收工前可选硬门「至少成功一次或声明跳过」。  
2. **写后诊断软反馈（V0.5）**：语法/轻量 lint，只回灌本写引入错误——取「写后反馈」思想；**不上** Hermes 级多语言 LSP 守护进程。  
3. 任务级 Docker/云后端：**另案 ADR**，明确非办公良品前置，也非 Bot 网关配套。

### 阶段 E — 度量与收口

- 指标：integrity 一次通过率、假后缀率、专用工具调用占比、test_runner 占比、软放行率、（可选）预览返工轮次。  
- 项目收口：完整性失败汇总进补建候选。

## 六、推荐落地顺序（拍板用）

```
A1 write 拒二进制后缀          ← OpenCode 同构，立刻做
A2 完整性校验+nudge
B1 slide_generator / arch_diagram 增强
B2 docx + sheet（自研 V0 或 MCP/CLI ADR）

E  度量
```

**不建议**：继续 `write_file` 造 pptx/png；或先上完整多模态/完整 LSP/全量 Docker 再堵假文件。

## 八、风险与边界

- 外挂 Office MCP/CLI：许可证、体积、Windows → **必须 ADR**；接入须服从 READ_ONLY/ENRICH/VALIDATE/CONTROL。  
- 视觉多模态：费用与隐私 → V0 规则预览即可。  
- 拒写二进制 → 靠 nudge + 工具描述补偿（阶段 A 必做）。  
- 页数≥6 等审美不进 Core 硬闸；Core 保 **真实 + 可打开 + 基本结构**。  
- 对照文案若写成「做成 Hermes/Grok Bot」一律视为越界——本项目交付面是 **桌面项目工作台 + 产物清单**，不是 IM Bot。

## 十、非目标

- **不做** Hermes Bot Mode / Messaging Gateway / Grok Bot 类常驻对话助手产品化。
