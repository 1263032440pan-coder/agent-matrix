# 修改方案：节点产物达成率提升（P0～P2）

> 版本：2026-10-30（初稿，待评审）  
> 前置：令牌 Stop + 返工 3 次 + 软放行（SYS-138～140）；工具预算 Grace / Continue nudge；单节点用户 Rework（SYS-143～146）  
> 状态：**P0～P2 已实施（SYS-147～161）**（本文为唯一方案文档，不另立 ADR；RTM 自 SYS-147）  
>
> **已拍板：**  
> 1. `file_rw` **拆分为 `read_file` / `list_dir` / `write_file`**（另加 P1 的 `append_file`），从结构上消除「写被当成读」。  
> 2. **分批落地**：P0 先单独合入，以 #15 回放验收通过后再开 P1。  
> 3. 计划期文件清单（SYS-158）**不强制**，只提醒。  
> 4. 节点验证等级（SYS-159）**不进 Gate 判定**，只展示。  
> 触发样本：项目 2 / 任务 #15「工作者执行」用户 Rework 后仍软放行，缺 `readme*` 与 `*.java`。

---

## 一、问题定性

把「节点交出要求产物」拆成三个条件概率，再乘上失败后被纠正的恢复概率：

```text
P(产物达成) ≈ P(理解需求) × P(计划正确 | 理解) × P(工具执行正确 | 计划) + 恢复项
```

#15 本轮的损失全部落在 **P(工具执行正确)** 和 **恢复项** 上。模型理解了需求，列出了 11 个待写文件（含 `README.md`），计划没有问题。

### 1.1 事实（#15 Rework 后一轮）

| 观测 | 数据 |
|--|--|
| `file_rw` 调用 | 30 次，约 20 次 `ok=False` |
| 模型看到的「写入」结果 | 新文件返回「文件不存在」；已有文件返回**原内容** |
| 模型结论 | 「write 有配额，已用尽」（臆测），之后放弃写入，只写说明 |
| 结局 | 返工 3 次后 `UNMET_AFTER_EARLY_STOP` 软放行，`output.v2.md` 仅 89 字节 |

### 1.2 根因

1. **写请求被静默降级成读**。`FileRwProvider.invoke` 的 `action` 缺省为 `"read"`（`tools.py:110`）。上表两种返回只可能来自 read 分支：write 分支只回「已写入 X: N 字符」。`action` 丢失有两条途径，现有审计无法区分：
   - 模型漏传 `action`。schema 虽把它列为 `required`，运行时并不校验。
   - 长 `content` 流式截断后，`_repair_arguments`（`llm_worker.py:105`）补齐了闭合符，但排在 `content` 之后的 `action` 已经丢失。修复后不校验必填字段，半截请求被当作合法请求执行。
2. **读写路径语义不一致**。注入 `__ws_root` 后，write 把 `README.md` 解析到任务工作区；read/list 走 `_resolve`，用 `Path.cwd()/README.md` 解析，结果是越界或不存在。模型「写后读回自检」得到反证，越发确信写入失败。
3. **错误反馈不可行动**。报错只有一句自然语言，没有错误类别，也没有正确调用示例。模型只能猜原因，最后猜成了「配额」。
4. **审计缺失**。`LLM_TOOL_CALL` / `LLM_TOOL_RESULT` 只记录 `tool`、`ok` 和字数，不记录 action、path、错误文本。本次诊断只能从思维链反推。
5. **返工反馈不升级**。3 次返工的 nudge 都是「请立即用工具补齐」。第 2、3 次没有附上工具失败统计，模型拿不到新信息。
6. **Rework 继承旧叙事**。重跑时模型在上下文里读到「上次写入失败」，一开始就带着「工具坏了」的先验。
7. **环境验证能力与技术栈不匹配**。#15 是 Java/Spring 项目，但 `tool:builder` 只支持 `npm_build` / `docker_build`，shell 白名单也没有 `mvn` / `javac`，产物写出来也无法编译验证。

### 1.3 不采纳

| 做法 | 为何不做 |
|--|--|
| 调大 `_TOOL_ROUNDS` 或 `_DELIVERY_REPAIR_MAX` | 工具本身在误路由，多给轮次只会多失败几次 |
| 让 `file_rw` 在缺 `action` 但带 `content` 时自动推断为 write | 截断场景下 `content` 本身可能是半截，自动写入会落盘残缺文件；必须显式报错让模型重发 |
| 保留 `file_rw` 单工具、只加 `action` 严格校验 | 能让误路由不再静默，但模型仍可能漏传 `action`，每次都要多耗一轮纠错。拆成单一用途工具后，「写」只能调 `write_file`，这类错误在结构上不存在 |
| 取消软放行 | 软放行是兜底，不是根因；去掉只会把「缺口可见」变成「整节点 FAILED」 |
| Worker 直接改 Task 状态以跳过 Gate | 违反 Proposal → Core Validation → State Transaction |
| 新增 Extension Point（如「工具结果后置钩子」） | 本方案全部落在既有 Worker 工具循环和 TOOL Provider 内部，不需要新 Hook |

## 二、目标与度量

| 指标 | 定义 | 目标（P0 落地后，以 #15 同类任务重跑为准） |
|--|--|--|
| 首轮交付率 | 首次 Stop 即通过令牌检查的 TaskRun 占比 | 明显上升（以 SYS-161 基线为准） |
| 软放行率 | `DELIVERY_GAP_ACCEPTED` / Gate PASS | 下降 |
| 写入误路由 | 意图为 write 却进入 read 分支的调用 | **0**（结构上不可能） |
| 工具错误可诊断率 | 失败结果带 `error_code` 的比例 | 100% |

## 三、P0：工具可靠性（直接解决 #15 这类问题）

### 3.1 `file_rw` 拆分为三个单一用途工具（SYS-147）

**新工具**

| 工具 | 参数（全部必填，除注明外） | 行为 |
|--|--|--|
| `tool:read_file` | `path` | 读文件，返回内容（截断上限同现行） |
| `tool:list_dir` | `path`（可选，缺省为本任务工作区根 `.`） | 列目录，返回相对路径列表 |
| `tool:write_file` | `path`、`content` | 新建或覆盖文件；禁闭、冻结校验脚本保护与现行 write 分支一致 |

- 三个工具都没有 `action` 参数，也没有任何缺省分派。必填参数缺失时返回 `MISSING_FIELD`，**不执行**。
- schema 描述各自只讲一件事，例如 `write_file`：「在本任务工作区新建或覆盖文件；相对路径以本任务工作区为根；没有写入配额；长内容请分段（见 `append_file`）」。
- 三个工具共用同一个 Provider 内部实现（路径解析、禁闭、错误构造只写一份），对外注册为三个 TOOL Provider。

**旧名兼容**

- `tool:file_rw` 不再出现在暴露给模型的工具列表中。
- 白名单解析时做**别名展开**：Agent 定义的 `plugins` 里出现 `file_rw`，展开为 `read_file`、`list_dir`、`write_file`（P1 起含 `append_file`）。原因：`USER` / `CONTROLLER_GENERATED` 来源的 Agent 定义存于数据库、seed 永不覆盖，不能靠改内置模板完成迁移。
- 内置模板（`registry.BUILT_IN_TEMPLATES`）与 `derive.BASELINE_PLUGINS` 直接改为新名，seed 的 upsert 会同步 `BUILT_IN` 行。
- 模型仍调用 `tool:file_rw`（会话历史或幻觉）时：返回 `TOOL_RENAMED`，`hint` 给出三个新工具的调用示例，不执行任何读写。
- `__ws_root` 注入名单从 `tool:file_rw` 改为三个新工具（`slide_generator` 保持）。
- Gate / Stop 返工提示里「用 file_rw 落盘」的文案改为「用 write_file 落盘」。

**同类缺省分派一并收紧**：`tool:builder` 的 `kind` 缺省为 `npm_build`，`slide_generator` 等也要排查。规则一致：缺省即报错，不静默选分支。

**不变**：`ArtifactManager` 的产物登记靠工作区前后快照差异，不依赖工具名；拆分不影响 harvest。

### 3.2 截断修复后校验必填字段（SYS-148）

- 拆分后 `action` 丢失的问题不复存在，但长 `content` 截断仍会发生：截断可能丢掉 `content` 之后的字段，或者 `content` 本身是半截。
- `_repair_arguments` 修复成功后，按该工具 schema 的 `required` 校验修复结果；缺字段即不调用 Provider，直接返回 `TRUNCATED`，`hint`：「参数在传输中被截断（已收到 N 字符），请把内容拆成多次较短的写入（P1 起可用 `append_file`）」。
- 字段齐全但经过修复的 `write_file`：`content` 很可能是半截。仍执行写入（避免整轮作废），但回执明确提示「本次内容经截断修复，可能不完整，请 `read_file` 检查文件末尾」，审计记 `repaired=true`。
### 3.3 读写路径语义统一（SYS-149）

- 注入 `__ws_root` 时，`read_file` / `list_dir` / `write_file` 使用**同一个解析函数**：相对路径一律以任务工作区为根；`data/tasks/...` 前缀与重复任务前缀的剥离规则沿用现行 write 逻辑。
- 读的范围仍可覆盖整个 `data/tasks`（读上游产物需要），写仍只限本任务工作区。两者差别只在「允许范围」，不在「相对路径基准」。
- 未注入 `__ws_root`（非任务上下文）时保持现行 `_resolve` 行为。
- `list_dir` 的输出改为相对任务工作区的路径，模型拿到即可原样用于 `read_file` / `write_file`。

### 3.4 结构化错误（SYS-150）

工具失败统一返回：

```json
{
  "ok": false,
  "error_code": "MISSING_FIELD | TOOL_RENAMED | TRUNCATED | NOT_FOUND | OUT_OF_SCOPE | FORBIDDEN_PATH | IO_ERROR",
  "error": "人类可读说明",
  "hint": "下一步怎么做，含一条正确调用示例"
}
```

- 喂回模型的文本格式固定为 `[error_code] error\n建议：hint`。
- `OUT_OF_SCOPE` 的 hint 写明本任务工作区的相对根，以及「其他任务目录只读」。
- 写入成功的回执补充：相对路径、字节数、本任务工作区当前文件数。

### 3.5 工具审计补齐（SYS-151）

- `LLM_TOOL_CALL`（非搜索工具）payload 增加：`path`、`kind`（有则记）、`content_chars`、`repaired`。**不记录 content 正文**。
- `LLM_TOOL_RESULT` payload 增加：`error_code`、`error`（前 300 字）。
- 现有事件类型不变，只扩字段，不新增事件类型。

## 四、P1：调用链、上下文与反馈闭环

### 4.1 写入后增量缺口回执（SYS-152）

- 每次 `write_file` / `append_file` 成功（及 `slide_generator` 等落盘工具成功）后，Worker 用 `check_obligation_tokens_detailed` 对本任务目录做一次检查，把结果附在工具回执末尾：
  - 有缺口：`剩余缺口：readme*（建议路径 README.md）；*.java ≥1`。
  - 无缺口：`义务令牌已全部满足，可以收工`。
- 只读文件系统，零 LLM 调用。检查失败（异常）时不附回执，不影响工具结果。
- 收工 Stop 硬闸保持不变；本项只把发现缺口的时间从结尾提前到过程中。

### 4.2 义务令牌转可读清单 + 开工注入工作区现状（SYS-153）

- Worker prompt 的【义务令牌·收工必过】段，在令牌原文之外加一份**人类可读清单**，每项带示例路径：
  - `prefix:d1:readme` → 「根目录需有 README.md（文件名以 readme 开头，大小写不限）」
  - `ext:d1:any` → 「至少 1 个源文件，扩展名属于 .py/.ts/.js/.go/.java/.rs/.md」
  - `count:d1:N` → 「至少 N 个常规文件」
- 开工时注入：本任务工作区目录树（相对路径，最多 100 项）+ 当前缺口清单（同 4.1 的检查结果）。
- 系统提示补一条事实：「本任务工作区可自由新建/覆盖文件，没有写入配额；其他任务目录只读。」

### 4.3 Rework 上下文净化（SYS-154）

- 用户 Rework 或 Gate 打回后的重跑：上下文里**不注入**上一轮的工具失败叙述或模型自述。
- 改为注入结构化事实：上一轮缺口清单、上一轮工具错误码统计（例如 `MISSING_FIELD×18, OUT_OF_SCOPE×2`），以及「工具实现已修正/无配额」的明确说明。
- 会话记忆（`session_store`）的复用规则不变，只调整重跑时拼进 prompt 的那一段。

### 4.4 连续失败熔断诊断（SYS-155）

- 同一工具连续失败 3 次，或一轮内同一 `error_code` 累计 ≥3 次：在下一轮前注入一条诊断消息，内容是：
  - 最近几次失败的 `error_code` 与参数要点（工具名/path，不含正文）；
  - 一条正确调用示例；
  - 「这是参数问题，不是配额或权限问题」（按实际错误码措辞）。
- 每个任务每轮最多注入 2 次，避免刷屏。
- 记录事件 `TOOL_FAILURE_DIAGNOSIS`（新增事件类型，只读审计用途，不改状态）。

### 4.5 新增 `append_file` 工具（SYS-156）

- `tool:append_file(path, content)`：文件不存在则创建，存在则追加。写入禁闭、冻结校验脚本保护、路径解析与 `write_file` 完全一致。
- schema 描述写明：长文件请先 `write_file` 首段，再多次 `append_file`，单次 `content` 建议 ≤ 6000 字符。
- 旧名 `file_rw` 的别名展开从此包含 `append_file`。
- 与 3.2 的 `TRUNCATED` hint 联动。

### 4.6 返工 nudge 升级（SYS-157）

现行 3 次 nudge 文案相同。改为逐次升级：

| 次数 | 附加内容 |
|--|--|
| 第 1 次 | 缺口清单 + 每项建议路径（同 4.2 的可读清单） |
| 第 2 次 | 第 1 次内容 + 本轮工具错误码统计 + 一条针对最高频错误码的正确调用示例 |
| 第 3 次 | 第 2 次内容 + 「仅需补齐以下文件即可收工」的最小动作清单（逐个文件、逐条调用） |

`_DELIVERY_REPAIR_MAX` 保持 3，软放行规则不变。

## 五、P2：计划校验、执行环境与度量

### 5.1 计划期文件清单校验（SYS-158）

- Worker 首轮被要求先输出一份「将要产出的文件清单」（相对路径列表，结构化 JSON）。
- 系统用令牌规则对这份**计划清单**做一次离线校验（把路径当成虚拟文件跑 `check_obligation_tokens_detailed` 的匹配逻辑）。不覆盖令牌时立即回一条纠正消息，让模型补计划，然后再开始写。
- 清单只作为执行期参照，不进 Task Graph、不改 `delivery_manifest`、不改令牌。
- 首轮未给清单不报错（兼容），只在 nudge 里提醒。

### 5.2 按技术栈补齐构建验证（SYS-159）

- `tool:builder` 的 `kind` 增加：`mvn_compile`（`mvn -q -o compile` 或 `mvn -q compile`）、`py_compile`（对工作区 `*.py` 做 `python -m py_compile`）、`tsc_noemit`。命令依旧是白名单固定形态，不开放任意参数。
- 运行前探测可执行文件是否存在；不存在时返回 `TOOLCHAIN_MISSING`，`hint` 写明「当前环境无法编译验证此技术栈，请确保源码完整并在 README 中写明构建命令」。
- 规划期在节点上标注**验证等级**（`compile` / `syntax` / `none`），展示在 Dashboard 节点详情，供用户判断产物可信度。只读标注，不影响 Gate 判定。

### 5.3 shell 白名单平台适配（SYS-160）

- `tool:shell` 以 `shell=True` 执行；Windows 下 `ls`/`cat`/`head`/`tail`/`grep`/`wc`/`find` 是否可用取决于环境（`cmd.exe` 无这些命令，`find` 语义也不同）。实施时先实测。
- 不可用的命令从 schema 描述与白名单中按平台剔除，或映射到等价命令（如 `dir`、`type`）。目标：模型看到的命令都能真实执行，不让它在不可用命令上浪费轮次。

### 5.4 交付质量度量（SYS-161）

- Runtime 只读聚合（来自 TaskRun 与事件，不新增写路径）：
  - 每节点：首轮交付率、返工次数、是否软放行；
  - 每项目：软放行率、各 `error_code` 频次、截断修复次数（`repaired=true`）。
- 通过既有 Dashboard API 增字段返回；Desktop 先以文本/小表格展示，不做图表。
- 作为 P0/P1 效果的验收基线：P0 上线前先跑一次采集基线。

## 六、边界与约束

| 约束 | 本方案的处理 |
|--|--|
| Stable Kernel 不被插件直接修改 | 全部改动在 Worker 工具循环与 TOOL Provider 内部；不改 FSM、Task Graph、Gate 判定规则 |
| 插件权限 READ_ONLY / ENRICH / VALIDATE / CONTROL | `write_file` / `append_file` 仍只落任务工作区并经 harvest 登记 Artifact；不引入 DIRECT_STATE_MUTATE |
| 工具拆分是否算新 Extension Point | 不算。新增的是 TOOL 能力下的 Provider，挂在既有工具分发点上，与 `git`、`builder` 等同级；不新增 Hook 点 |
| 编码修改走 Proposal → Core Validation → State Transaction | 状态变更路径不变；本方案不新增任何状态转移 |
| Extension Point 稳定 ID | 不新增 Hook 点；新增的只有事件类型 `TOOL_FAILURE_DIAGNOSIS`（审计用途） |
| Automation Mode 只有 FULL_AUTO / MANUAL | 不涉及 |
| Resource Governor 与 Automation Mode 正交 | 不涉及；`_TOOL_ROUNDS` 等预算不调整 |

### 明确不做

1. 提高工具轮次上限或返工次数上限。
2. 保留 `file_rw` 作为模型可见工具，或对它做参数推断后继续执行。
3. 取消或放宽软放行与 Gate 规则。
4. 让 Worker 修改令牌、清单或冻结校验脚本。
5. 开放任意 shell 命令或任意构建参数。
6. 在本方案内引入 Embedding/向量检索等上下文增强插件。

## 七、实现要点

1. `tools.py`：`FileRwProvider` 拆为 `ReadFileProvider` / `ListDirProvider` / `WriteFileProvider`（P1 加 `AppendFileProvider`），共用一个内部模块处理路径解析、禁闭、冻结脚本保护与错误构造；所有失败分支返回 `error_code` + `hint`。同步收紧 `slide_generator` / `builder` 的缺省分派。
2. `tool_schemas.py`：删除 `FILE_RW_SCHEMA`，新增四个单一用途 schema，描述写明「相对路径以本任务工作区为根」「长内容分段」「无写入配额」。
3. 白名单与模板：
   - 白名单解析处（`_search_tools` 及 `_run_tool_plugin` 的白名单判定）加 `file_rw` 别名展开。
   - `registry.BUILT_IN_TEMPLATES`、`derive.BASELINE_PLUGINS` 改为新名。

## 八、验收

1. **#15 回放**：对项目 2 任务 #15 再次用户 Rework（P0 合入后），在不改令牌与模型的前提下，交出 `README.md` 与至少 1 个 `.java` 文件，Gate PASS 且最新 TaskRun 无 `delivery_gap`。
2. 暴露给模型的工具列表中没有 `file_rw`，有 `read_file` / `list_dir` / `write_file`；`write_file` 缺 `content` 返回 `MISSING_FIELD`，工作区无变化。
3. 调用 `tool:file_rw`：返回 `TOOL_RENAMED` 与新工具示例，不读不写。
4. 数据库中 `plugins` 含 `file_rw` 的 USER Agent：执行时可用三个新工具（别名展开生效）；BUILT_IN 模板 seed 后为新名。
5. 构造截断参数（`write_file` 只收到 `{"path":"a.md"`，`content` 丢失）：返回 `TRUNCATED`，Provider 未被调用；字段齐全但经修复的写入，回执带「可能不完整」提示且审计 `repaired=true`。
6. 同一相对路径 `README.md`：`write_file` 后立即 `read_file` / `list_dir`，三者解析到同一个任务工作区文件。
7. `write_file` 写其他任务目录：返回 `OUT_OF_SCOPE`；`read_file` 读其他任务目录仍可成功。
8. 事件表中 `LLM_TOOL_CALL` 含 `path`/`content_chars`/`repaired`，`LLM_TOOL_RESULT` 失败时含 `error_code`/`error`；两者均不含 content 正文。
9. 写入成功回执末尾带剩余缺口；补齐最后一项后回执显示「已全部满足」。
10. 人为制造连续 3 次 `MISSING_FIELD`：下一轮前出现诊断消息，事件表有 `TOOL_FAILURE_DIAGNOSIS`；同轮最多 2 次。
11. 第 2 次返工 nudge 含错误码统计与调用示例；第 3 次含最小动作清单。
12. `write_file` + 多次 `append_file` 能拼出完整文件；冻结校验脚本仍禁止写入和追加。
13. 无 `mvn` 的环境调用 `mvn_compile`：返回 `TOOLCHAIN_MISSING` 与 hint，不抛异常。
14. Dashboard 可看到节点验证等级与项目软放行率、错误码频次。
15. 既有测试全绿（含 `test_whitelist_enforcement`、`AgentPanel.test.tsx` 改名后）；Gate、FSM、软放行、用户 Rework 行为无回归。
