# 返修单：软件开发需求三件必然交付闭环（V1.5b）

> 版本：V1.5b（2026-10-22，用户两项拍板后定稿）
> 前置：`返修单-V1.5a-1后-代码产出闭环四缺陷.md` 先行（P0 安全项是本单前提）
> 用户拍板（2026-10-22）：
>   ① 缺产物 → **自动补建任务**（对账闭环语义，任务真实执行）
>   ② PPT → **要保证质量**（不只查存在性）
> 原则不变：WHAT 约束（交付完整性）收进系统机制，WHERE 安排（阶段归属）完全放开给 AI。

---

## 一、总体设计

```
用户资料（任意形态）→ /plan 链
  ├─ ① delivery_classifier 语义判定（normalize 后新阶段）
  │     → Project.delivery_profile = SOFTWARE_DEV | NOT_SOFTWARE
  ├─ ② 判定 SOFTWARE_DEV → llm_extractor prompt 注入三件必然交付契约
  │     → AI 自行决定三件在哪个阶段/哪个任务产生（不约束流程设计）
  │     → 任务带 delivery_tags: [ppt, code, test_report]（复用 code_stage 透传通道）
  ├─ ③ 项目收口：末任务 ACCEPTED 时 ProjectDeliveryValidator
  │     → PPT 存在+质量达标 / 代码+README / 测试报告
  │     → 缺 → RECONCILIATION_GAP → 自动补建"交付补全"任务（对账循环既有路径）
  └─ ④ UI 三件状态行（✅/❌/已补建）
```

## 二、六个部件

### ① 语义判定器（新机制，~120 行）

**位置**：`project_runtime/procedure/delivery_classifier.py`（新文件）。

**判定链**（三级降级，绝不断链）：
1. LLM 语义判定（主通道）：normalize 后、assess 前调用，prompt 明确——
   "材料要求**开发/构建软件**才 SOFTWARE_DEV；纯需求调研、软件选型评估、操作手册、流程规范类文档 NOT_SOFTWARE"。输出 JSON `{"software_dev": true|false, "reason": "..."}`
2. 无 LLM（测试态）：`_material_requires_code` 正则扩词表（加"开发文档/接口文档/系统设计/数据库表/部署"等）兜底
3. 双通道均失败 → NOT_SOFTWARE（保守：不注入约束，用户手动补）

**落库**：`Project.delivery_profile` 列（migration `xxxx_add_delivery_profile`，String(32) nullable——存量项目 NULL=未判定，语义同 NOT_SOFTWARE）。

**UI 可见**：项目卡片"识别为软件开发需求 · 交付基线：PPT/代码/测试报告"。

### ② 交付契约注入（生成侧——AI 自主安排的实现点，~30 行）

**位置**：`llm_extractor.py` 的 prompt 组装。

判定 SOFTWARE_DEV 时，节点抽取 prompt **末尾**追加：

> 本项目最终交付物必须包含三件：①项目方案介绍 PPT ②可运行的代码（多文件组织+README+依赖说明）③测试报告。
> 这三件在流程的哪个阶段、哪个任务产生，**由你根据材料自行安排**——约束的是交付完整性，不约束流程设计。
> 承载任务请在节点 outputs 里体现对应产物。

**透传**：planner 建 playbook_ref 时，节点 outputs 含 ppt/pptx/演示/汇报 → `delivery_tags += ["ppt"]`；含 源码/代码/实现 → `+= ["code"]`；含 测试报告/测试 → `+= ["test_report"]`（规则表，不进 LLM——归一判定是机制）。`delivery_tags` 进 playbook_ref JSON（与 code_stage 同槽位扩展）。

### ③ 项目收口 Gate（校验侧，~100 行）

**位置**：`project_runtime/reviewer/gate.py` 加 `ProjectDeliveryValidator` + service.py 末任务 ACCEPTED 钩子。

**触发**：项目最后一个任务 Gate PASS→ACCEPTED 后（execution service 的 `_auto_advance` 尾部判断"无 READY/RUNNING/CREATED 残留"），且 `delivery_profile=SOFTWARE_DEV`。

**判据**：

| 交付物 | 存在性 | 质量线（PPT 专属——用户拍板②） |
|---|---|---|
| PPT | 项目 artifact 全集含 .pptx | **质量三查**（见 ③-2） |
| 代码 | ≥1 代码文件 + README + 依赖说明（requirements.txt/package.json 其一） | 无（任务级四缺陷 Gate 已覆盖结构） |
| 测试报告 | md 含"测试"且含结论段（通过/失败统计） | 无 |

**③-2 PPT 质量三查**（机制可查的结构指标，非审美）：
1. **页数 ≥ 6**（python-pptx 读 slide count；封面+目录+方案+架构+计划+结尾的下限）
2. **非空页占比 ≥ 80%**（每页至少 1 个内容 shape——防空壳页）
3. **含结构要素**：至少 1 页有标题+正文双要素；封面页有项目名（读 slide[0] 文本含项目 name 或其关键词）

三查不过 → 与缺失同等处理（RECONCILIATION_GAP + 补建任务，契约注明"PPT 质量未达标：页数 X<6/空页多/缺封面"——给补建任务明确的修复目标）。

**缺失/不达标 → 自动补建**（用户拍板①）：
- 复用对账循环既有路径：`RECONCILIATION_GAP` 事件 → 补建任务（名称"交付补全-{缺失件}"，契约列缺失明细+质量判据），状态 READY 直接可执行
- 补建任务也带 delivery_tags（知道自己补什么）
- **防死循环**：同项目同缺失件补建次数 ≤ 2（第二次仍缺 → 事件升级 `DELIVERY_GAP_UNRESOLVED`，UI 标红，留给用户——不再自动补）

### ④ slide_generator 质量增强（保证 PPT "生得出且生得好"，~60 行）

现状：tools.py slide_generator md→pptx 已实现，但无质量约束。

- 生成后自查（复用 ③-2 三查逻辑调用），不过 → 返回可理解错误喂回模型（"生成 PPT 仅 3 页，请按 {质量线} 补充内容后重新生成"）
- schema 描述补质量线（行为指引进 schema 文档字符串——这是工具契约不是行为模板，合规）

### ⑤ UI 三件状态（~40 行）

项目详情顶行：`方案PPT ✅ | 可运行代码 ✅ | 测试报告 ❌→已补建任务 #12`。
数据源：收口校验结果存 `project_playbook` 表附列（或轻量表），Dashboard 轮询读。

### ⑥ 测试（~180 行）

- 判定器：SOFTWARE_DEV 正例（开发文档/口头需求"做个工具"）/ 反例（操作手册/选型报告）/ 无 LLM 兜底 / 双失败保守
- prompt 注入断言：SOFTWARE_DEV 时 extractor prompt 含三件清单原文
- delivery_tags 归一：outputs 词表命中
- 收口 Gate：三件齐 PASS / 缺 PPT 补建 / PPT 3 页空壳 → 补建（质量三查）/ 补建 2 次上限
- slide_generator 自查不过喂回
- 全量回归

## 四、验收

- [ ] 迷你待办 CLI 需求（test-assets）全链：判定 SOFTWARE_DEV、AI 自安排三件归属、产物齐三件、PPT ≥6 页非空、Gate PASS

- [ ] 补建 2 次仍缺 → 停止自动补 + DELIVERY_GAP_UNRESOLVED 事件 + UI 标红

## 五、Out of Scope

- PPT 审美/配色/排版（结构三查之外的质量属 skill 层——可选 skill 1.1.2 加 PPT 撰写指引，版本化升级不碰代码）
- 测试报告质量（只查含结论，跑没跑真测试属硬门观察——附录草案仍等拍板）
- 代码质量检查（lint/复杂度）——LSP 在 20号规范 Out of Scope 清单里
- 判定器多语言/方言（V0.1 中英文词表）
