# 设计单：代码工程产物能力——契约/产物模型/反馈环三件套

**单号**：设计-20号-V1.5-代码工程产物
**日期**：2026-10-21
**背景**：真实项目实测（项目#1 个人任务看板）暴露——Agent/插件/工具循环全链已通（V1.4g/h/i 三修后 write 可靠落盘），但产出物仍是纯文档。用户文档 16 节明确要求"项目源码"交付，系统无承接能力。
**定位**：这不是修 bug——是给执行链补"代码工程"这一产物语义。三件套互相咬合，缺一不可。

---

## 一、问题定位（为什么现在生成不了软件项目）

```
能用的都齐了:  5 环节 Agent ✓ / 11 插件（file_rw/shell/git/test_runner/builder）✓
              / 工具循环 12 轮 ✓ / write 长内容落盘 ✓（V1.4i 修复）

缺的三层:
  ① 任务没要求——Planner 生成的契约全是文档型（skill 九阶段的产出物
     模板就是文档），"项目源码"交付物没被翻译进任务契约
     → 模型很听话: 契约要文档它就写文档
  ② 产物只认单文件——Worker 收工只登记 {任务名}_output.md 一个官方产物;
     模型工具循环里散写的工作区文件不进 Artifact 表
     → 即使模型真写了 10 个代码文件，系统眼里"产物"还是那一个 md
     （UI 看不见 / Gate 不验收 / 下游不知道）
  ③ 没有"跑通"标准——没有写完必须跑测试的纪律，也没有失败喂回重写的环
     → "写完"≠"能运行"，代码质量无闭环
```

**边界澄清（用户问询确认）**：
- 不修改 skill 包——`software-project-delivery` 的 stages 是通用方法论（"开发阶段产出实现"没错）；增强发生在 Planner **实例化到具体项目**时（材料约束高于 skill 模板——双向规则）
- Controller 实体化不在本单范围——契约生成改在现有函数链（builder/Planner）上做，Controller 将来实体化时逻辑直接迁移（路径 A，用户已知悉选择）

## 二、修改方案

### 第①件：契约生成——交付清单驱动的代码工程条款（~半天）

**位置**：`project_runtime/playbook/builder.py`（产出物融合处）+ `project_runtime/planner/planner.py`（契约落任务处）

**机制**：新增"交付物类型识别"环节，链路如下：

```
/plan 时:
  ① 扫描项目交付清单——数据源两个:
     a. 用户文档的方法资产原文（正则命中: 源码/代码/可运行/工程/
        启动/编译 等交付物关键词，命中 16 节"项目源码"这类条款）
     b. method_asset 的 expected_outputs 字段（若文档结构化过）
  ② 命中"代码类交付物" → 置项目级标志 code_delivery_required
  ③ Planner 给「开发实现」类任务（stage=开发实现）生成契约时叠加条款:

     【代码工程条款】（叠加在原文档型产出之上，不替换）:
     - 产出可运行的代码工程: 按模块组织多文件（入口文件/功能模块/测试文件）
     - 每个文件用 file_rw 独立落盘（data/tasks/{pid}/{tid}/ 下按目录组织）
     - 附 README.md: 启动方式、依赖清单、文件结构说明
     - 完成前用 test_runner 跑测试并确保通过（配合第③件强制门）
  ④ Gate 验收联动: 该类任务的验收对照项追加"多文件存在 + README 存在"
     （布尔式——符合验收冻结原则，不搞语义判断）
```

**契约条款模板**（写死在代码里的结构化模板，非 LLM 生成——确定性可测）：

```python
_CODE_DELIVERY_CLAUSE = {
    "require_code_project": True,
    "files": {
        "entry_file": "必需——程序入口（如 main.py / index.js）",
        "modules": "按功能拆分的模块文件",
        "tests": "至少一个测试文件",
        "readme": "README.md——启动方式/依赖/结构",
    },
    "organization": "data/tasks/{pid}/{tid}/ 下子目录组织（src/ tests/）",
    "must_pass_tests": True,   # 与第③件咬合
}
```

**不做的**：不识别具体技术栈（Python/JS 由模型依上下文自决——契约只约束"多文件+可运行+有测试"的形态，不定语言）。

### 第②件：产物模型——工作区文件全量登记 Artifact（~一天）

**位置**：`project_runtime/worker/llm_worker.py`（收工点）+ `project_runtime/artifact/manager.py`（登记 API）+ `apps/desktop/src/components/Dashboard.tsx`（文件树展示）

**机制**：

```
Worker 收工（_archive_session 前新增 harvest 步骤）:
  ① 快照对比——任务开始时记下工作区（data/tasks/{pid}/{tid}/）文件清单
     （bind_agent 时或 assign 开始时拍快照）
  ② 收工时 diff: 新增/变更的文件 = 本次任务的产出物集
  ③ 全量登记 Artifact:
     - 每个新文件一条 Artifact 行（name=相对路径, version=1,
       logical_id=task-{tid}-{相对路径}）
     - 官方产物 {任务名}_output.md 保持现状（兼容既有 UI/验收链）
     - 文件树形态: logical_id 的路径结构天然构成树
  ④ ArtifactManager 扩展: batch_register(files) 批量接口
     （sha256 逐文件算——复用既有 hash 机制）

UI（Dashboard 产物区）:
  - 任务详情产物列表: 文件树缩进展示（src/ tests/ README.md 的层级）
  - ArtifactViewer 预览: 代码文件按文本预览（.py/.js/.md 通用;
    语法高亮不在本单——纯文本可读即可）

Gate 联动: code_delivery_required 任务验收时检查 Artifact 集
  （entry_file 存在 + README 存在——与第①件条款对应）
```

**排除的**：不做 zip 打包（交付时打包是 Delivery 阶段的事，本单只管登记与可见）；不改既有产物的 DB 结构（复用 Artifact 表，logical_id 编码路径）。

### 第③件：反馈环——代码任务收工前强制跑测试（~一天）

**位置**：`project_runtime/worker/llm_worker.py`（收工流程）+ `project_runtime/execution/service.py`（重写循环接入点）

**机制**：

```
Worker 完成 code_delivery_required 任务时（有最终 content 出口前）:
  ① 强制 test_runner 一轮:
     - 检测工作区测试文件（tests/ 下 *.py / *.test.js）
     - 无测试文件 → 视为未满足契约（README/模块要求里含测试）→
       喂回模型: "契约要求测试文件, 请补写后重试"
     - 有 → shell 跑 pytest（test_runner 插件，白名单已含）
  ② 结果二分:
     - 通过 → 正常收工（产物含测试报告摘要）
     - 失败 → 失败输出（退出码/失败用例名/错误摘要——test_runner
       已有结构化解析）喂回模型:
       "测试未通过: {失败摘要}。请修复代码使测试通过后重新交付。"
       模型在同一工具循环内继续（轮次预算内）或触发任务重写
  ③ 防死循环——与既有五闸咬合:
     - 修复重试上限 2 次（本环节独立计数, 不占 12 轮工具预算
       ——反馈环是收工前的独立校验循环）
     - 2 次仍失败 → 按契约如实交付"测试未通过"报告
       （REWORK 升级交给 Gate——Gate FAIL→REWORK 链既有）
     - 不自动降低测试标准（防"删测试保通过"——测试文件写定后
       本环节只跑不改）
```

**为什么独立循环而不是塞进 12 轮**：工具循环是模型的自主工作流；反馈环是系统的验收性校验——语义不同。塞一起会让"跑测试"挤占模型干活预算，且失败喂回的定位会乱。

## 三、三件咬合关系与实施顺序

```
①契约生成（半天）──→ 告诉模型"要写代码工程"（源头——没它模型继续写文档）
        ↓
②产物模型（一天）──→ 让写出来的文件"成为产物"（可见/可验收/下游可用）
        ↓
③反馈环（一天）──→ 让"写完"变成"跑通"（质量闭环）

实施顺序 = ①→②→③（每件独立可测; ①②完成时已有可见改善——
模型写出的代码文件出现在 UI; ③补上质量门）
```

**总体工作量**：~2.5 天。每件独立提交（三 commit），每件过全量测试。

## 四、测试计划

| 件 | 用例形态 |
|---|---|
| ① 契约 | 文档含/不含"项目源码"关键词 → 契约条款有/无（双向）; skill 产出物模板不被覆盖（文档型产出仍保留）; 条款结构断言（require_code_project/files/must_pass_tests） |
| ② 产物 | 模拟工作区新增 3 文件（含子目录）→ 收工 → 3 行 Artifact + 官方 md 并存; 快照 diff 只登记新增（任务前已有文件不重复登记）; UI 文件树渲染（vitest 缩进断言）; Gate 检查 entry/README |
| ③ 反馈 | 无测试文件 → 喂回补写; 测试失败 → 失败摘要喂回 + 模型修复 → 通过收工; 2 次重试上限 → 如实交付失败报告（不降标准不删测试）; 与 12 轮预算互不侵占（工具循环计数不变） |
| 集成 | 真实链路: 任务看板项目 → 生成计划（契约含代码条款）→ 执行 → 工作区 src/tests/README 落盘 + Artifact 文件树 + 测试通过收工 |

## 五、Out of Scope（明确不做）

- Controller 实体化（另立项——本单契约生成逻辑将直接迁移）
- 语法高亮/代码编辑器（UI 纯文本预览）
- 交付阶段 zip 打包（Delivery 域的事）
- 技术栈识别与限定（模型自决语言）
- LSP 插件（仍不实现——代码补全/跳转是另一量级的事）
- 测试标准的 LLM 生成（测试文件由模型按契约写, 反馈环只跑不判）
