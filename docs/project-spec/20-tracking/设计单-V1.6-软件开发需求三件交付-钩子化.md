# 设计单 V1.6：软件开发需求三件必然交付——钩子化实现

> 版本：V1.6（2026-10-22 定稿）
> 需求原文（用户）：
>   "对于任何一个用户输入的资料，只要在资料内容上大概意思是一个软件开发需求相关的，
>    在目前的产物基础上产物就必然要有项目方案介绍 ppt，可运行的代码，测试报告，
>    至于这些我要求的产物在流程的哪一个阶段产生是由 ai 自己觉得的"
> 实现原则（用户决策，2026-10-22）：**钩子化**——效仿开源开发智能体（Claude Code hooks /
> opencode）：代码层只提供"时机 + 事实 + 喂回"，验收标准与行为全部在 skill 层（可换可版本化）。
> **取代**：`返修单-V1.5b-软件开发需求三件必然交付闭环.md`（其 ProjectDeliveryValidator
> 质量三查/CodeDeliveryValidator 硬编码判据方案废弃；文件级 file_rw 禁闭等安全项并入本单）。

## 一、需求拆解与钩子化对照

| 需求要素 | 钩子化归属 | 落点 |
|---|---|---|
| "大概意思是软件开发需求相关" → 识别 | 机制（事实收集） | ① 语义判定器：LLM 判定结果落 `Project.delivery_profile`，**只记事实不做约束** |
| "产物就必然要有 PPT/代码/测试报告" | 行为（skill 声明） | ② skill 1.1.2《交付基线》节：三件清单+质量标准全在 skill 正文 |
| "必然"的强制力 | 机制（时机+喂回） | ③ Worker 收工自查钩子 + ⑤ 项目收口对账钩子——把事实喂给模型，判定归 skill 纪律 |
| "阶段由 AI 自己觉得" | 行为（安排自由） | ② 注入 extractor 的契约只说"交付完整性"，不说放哪；任务图 AI 自由设计 |
| PPT 质量 | 行为+工具事实 | ④ slide_generator 返回页数/空页等元数据（工具本该返回真实结果），标准在 skill |

## 二、总体流程

```
用户资料 → /plan 链
  ① normalize 后: delivery_classifier 语义判定（LLM 主 + 正则兜底 + 双失败保守不注入）
       → Project.delivery_profile = SOFTWARE_DEV | NOT_SOFTWARE（migration 新列）
  ② SOFTWARE_DEV → llm_extractor prompt 注入《交付基线》约定（仅 WHAT，不约束 WHERE）
       → AI 自由设计流程，三件归属任务自然带 delivery_tags（ppt/code/test_report 归一透传）
  ③ 每任务执行: Worker 收工自查钩子（时机=工具循环产出完成未收工）
       → 系统注入自查消息：工作区文件树 + 任务契约交付清单 + "对照 skill 验收纪律自查"
       → 模型按 skill 1.1.2 标准自查补齐；回合计入 12 轮预算（防死循环=预算制，非上限计数）
  ④ 工具事实: slide_generator 生成后返回元数据（页数/空页数/含文本页数）——判定归模型
  ⑤ 项目收口: 末任务 ACCEPTED 后触发对账钩子 → 既有 ReconciliationLoop
       → 输入=三件基线 vs artifact 全集，LLM 判定缺件 → 补建"交付补全"任务（既有路径）
  ⑥ UI: 项目卡片"软件开发需求 · 交付基线三件"标识 + 三件状态行
```

## 三、六个部件

### ① 语义判定器（机制，~120 行）

**新文件** `project_runtime/procedure/delivery_classifier.py`。

- 主通道：normalize 后 LLM 一次调用，prompt——"材料要求**开发/构建软件系统或工具**才
  SOFTWARE_DEV；纯需求调研、软件选型评估、操作手册、流程规范 NOT_SOFTWARE"。
  输出 `{"software_dev": bool, "reason": str}`
- 兜底：无 LLM（测试态）用扩词表正则（开发文档/接口文档/系统设计/数据库表/部署/实现）
- 双失败 → NOT_SOFTWARE（保守：不注入，用户可见标识可手动触发重新判定）
  **误判代价不对称（P2-3 如实声明）**：保守方向保护的是"非开发项目不被误伤"（操作
  手册不会被迫产代码）；反向代价是**开发需求被判 NOT_SOFTWARE 时三件基线静默不生效**
  ——用户以为"必然有三件"结果没有。兜底=UI 手动重新判定入口（见序 ⑥），
  **该入口可达性列入验收**（验收清单第 2 条）
- 落库：`Project.delivery_profile` String(32) nullable；存量 NULL 语义=NOT_SOFTWARE
- **判定结果纯事实记录**：它决定"注入不注入 skill 基线"，不直接约束任何产物

### ② skill 1.1.2《交付基线》节（行为，skill 包升级）

`software-project-delivery` 1.1.0 → **1.1.2**（跳 1.1.1 留作应急修复号），frontmatter
之后《执行纪律总则》内追加一节，**按 3000 字符窗口预算写**（P2-2 修正：窗口扩容
2000→3000 在序 0 先行做掉，是本节写入的前提——基线节估算 ~600 字符 + 既有纪律
总则 1399 字符 ≈ 2000，3000 窗口余量充足，**无需压缩既有段落措辞**；若实测超窗，
压缩对象是新写的基线节自身措辞，不动既有纪律）：

```markdown
## 交付基线（软件开发项目）

凡判定为软件开发需求的项目，最终交付必然包含三件，缺一不可：
1. 项目方案介绍 PPT——不少于 6 页；封面含项目名；每页有实质内容（非空壳）；
   建议结构：封面/问题与目标/方案总览/架构/计划/风险与结尾
2. 可运行的代码——src/ 多文件组织 + tests/ 测试 + README（启动方式/依赖/结构）；
   依赖清单必附（requirements.txt 或 package.json）
3. 测试报告——含测试范围、执行结果、通过/失败统计与结论

三件在哪个阶段、哪个任务产生，由你根据材料自行安排——本基线约束交付完整性，
不约束流程设计。收工自查时对照本清单逐项核对。
```

（正文为 skill 内容示意；实际措辞打包时定稿。**标准修改=发新版本，代码零改动**。）

**代码侧配套（机制，~25 行）**：llm_extractor prompt 尾部条件注入——
SOFTWARE_DEV 时追加"本项目交付基线见 skill《交付基线》节：PPT/可运行代码/测试报告三件
必然交付，阶段归属你自行安排"。**不复制 skill 正文**（与材料兜底同款边界）。

### ③ Worker 收工自查钩子（机制核心，~60 行）

**位置**：`llm_worker.py` 工具循环内，时机=模型产出完成信号但尚未收工（软提醒的强化泛化）。

```
触发条件（三全）：本任务 delivery_tags 非空（ppt/code/test_report 任一）
                且 模型已给出最终产出
注入消息（system 角色，一次性）：
  "收工自查：本任务契约要求交付〔delivery_tags 清单+stage_outputs〕。
   当前工作区文件清单：〔实际文件树——含文件名/大小/类型〕。
   已有 PPT 元数据：〔如有，页数/空页数〕。
   请对照 skill《交付基线》自查：缺什么补什么（可用 file_rw/slide_generator），
   齐了才输出最终交付。"
```

- 自查回合计入 **12 轮工具预算**（防死循环=预算制——模型在预算内自主权衡"补齐"还是
  "如实报告缺口"；预算尽 → 交付说明里写明缺口。opencode-solo 闭环本形）
- **一次性**：同任务第二次收工不再注入（放行，与软提醒同语义）
- **与硬门附录的关系（P3 声明）**：本钩子（预算内软机制）与附录硬门（独立 2 次修复
  循环）是两套机制，互不替代；硬门拍板决策不受本单影响。**自觉率统计口径更新**：
  自查钩子触发后的补齐行为计入自觉率数据（补了=自觉；被喂回才补=观察标签区分）——
  V1.6 上线后数据继续攒，口径变化在变更记录里登记
- 现有 `_soft_nudge_tests` 并入本钩子（三条件特例 → 泛化为 delivery_tags 驱动），
  删旧逻辑防双触发

### ④ slide_generator 事实返回（机制，~30 行）

生成 pptx 后读回元数据，**随结果一并返回**（不判定）：

```
{"ok": true, "path": "...", "slides": 9, "non_empty_slides": 8, "has_title_text": true,
 "stdout": "已生成 xx.pptx：9 页（8 页有内容）——请对照交付基线自查页数与内容要求"}
```

模型看到事实自己按 skill 判定（stdout 提示语即"提示"，判定标准不进代码）。

### ⑤ 项目收口对账钩子（机制接线，~70 行）

**位置**：service.py `_auto_advance` 尾部——项目无 READY/RUNNING/CREATED 残留 且
`delivery_profile=SOFTWARE_DEV` 时触发。

- 复用**既有 ReconciliationLoop**（controller.py 对账循环，20号规范批次 2 交付物）：
  输入=三件基线（skill《交付基线》同款清单文本）vs 项目 artifact 全集 + 工作区文件
- LLM 判定缺件/不达标 → 既有路径补建"交付补全-｛缺失件｝"任务（契约列事实：
  "项目 artifact 无 .pptx 文件"），任务 READY 可执行
- **防死循环=对账循环既有护栏**（补建任务本身带 delivery_tags，其收工自查会核它），
  不新设计数上限
- 事件落账：**新增 `RuntimeEventType.RECONCILIATION_GAP` 枚举值**（P2-1 修正：
  该枚举此前只存在于 controller.py:276 注释"批次 2 先登记"的欠账里，event/models.py
  并无此值——本单实施时新增，顺带清偿这条登记尾巴）

### ⑥ UI（~40 行）

- 项目卡片：`识别为软件开发需求` 标识（delivery_profile 轮询）
- 项目详情三件状态行：`方案PPT ✅ | 可运行代码 ✅ | 测试报告 ❌`（数据=轻量查询
  artifact 全集按扩展名/关键词汇总，展示事实不打分）
