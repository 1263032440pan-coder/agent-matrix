# 设计单 V1.6d：计划期冻结校验脚本 + 子进程收工闸

> 版本：V1.6d（2026-10-27，修订 2）  
> 前置：V1.6c（`delivery_manifest` + `deliverable_ids` + 进程内 match Stop 语义）  
> 用户决策：方案 **B**；脚本生成失败 → **整单计划失败（严格）** + **桌面 toast**；哈希漂移 → **任务 FAILED（不降级 match）**。

---

## 一、目标

1. 对齐 Claude Stop 的**外置闸**形态：校验在**冻结脚本 + 独立进程**，不在干活模型「心里完成」。  
2. **计划期生成一次**项目级 Python 校验脚本并落盘；content hash 锚定；收工禁止改写。  
3. 任务收工 Stop：subprocess 跑冻结脚本，传入本任务 `deliverable_ids`；不通过 → 同会话注入返工（≤3 → FAILED）。  
4. 脚本生成失败 / 契约不合 → **中止本轮规划**，API `error_code` + UI toast（用户必须看得见）。  
5. **保留** V1.6c 的 `delivery_manifest` / `deliverable_ids` / 节点「要求产物」；`match` 是生成输入与**差分冒烟**基准，**不是**运行时降级闸。  
6. 项目**收口**同样走冻结脚本（见 §五.2）。

### 1.1 使用前提（已拍板）

用户使用时**一定会传入材料**。空材料视为异常用法；计划链仍走抽取 → 生成器，失败则严格 422（不设「无材料跳过生成」的宽松分支）。

## 三、名词：收工 vs 收口

| 名词 | 时机 | 作用 |
|--|--|--|
| **收工（Stop）** | 单个任务拟终稿、本轮无工具调用 | 检查**本任务**认领的 `deliverable_ids` 是否已在**本任务工作区**落地 |
| **收口（Closeout）** | 项目内无进行中任务（全结束） | 用同一冻结脚本检查**总清单**是否在**项目工作区树**齐套；缺则补建「交付补全-…」并 submit |

工作区布局（已有）：

- 任务写盘：`data/tasks/{project_id}/{task_id}/`（file_rw 禁闭）  
- 项目根：`data/tasks/{project_id}/`（脚本文件也在此）  
- **产物归属约定**：某交付项挂在哪个节点，就必须落在该节点任务工作区内；禁止「A 任务认领、B 任务目录交差」。收口扫描项目根（递归子目录）只做齐套对账。

## 四、数据与落盘

### 4.1 项目级脚本文件

| 项 | 约定 |
|--|--|
| 路径 | `data/tasks/{project_id}/_delivery_validate.py` |
| 语言 | **仅 Python 单文件**（首版不做任意 shell） |
| 库字段 | `Project.delivery_validator_hash`（sha256，Text/String）；可选 `delivery_validator_generated_at` |
| Dashboard | 「交付基线」区展示：脚本已生成 / hash 前 8 位 / 生成时间（规划失败靠 toast；成功态也可见） |

### 4.2 脚本 I/O 契约（硬）

```text
python -I _delivery_validate.py --workspace <path> --ids id1,id2
```

- `--workspace`：Stop 传任务工作区；收口传项目根 `data/tasks/{pid}`。  
- `--ids`：逗号分隔；空则按契约返回 `ok=false` 或检查全部（生成 prompt 锁定：**空 ids → problems 含明确错误，不得静默 ok**）。  
- **stdout**：UTF-8 JSON（允许前后空白）：

```json
{"ok": true, "problems": []}
```

```json
{"ok": false, "problems": ["方案PPT: 缺少 .pptx"]}
```

- **exit**：`ok==true` → 0；否则非 0。Runtime **以 JSON 为准**，exit 辅助。  
- **禁区**：禁止写 SQLite / 调 Runtime API / 改 Project·Task；禁止网络；只读 `--workspace` 下文件。超时 **30s** 杀进程；stdout 大小上限（如 64KB），超限当失败。

### 4.3 生成输入

- 已校验的 `delivery_manifest`  
- 材料摘要 + skill 交付基线提示（与清单抽取同源，可截断）  
- Prompt：只输出完整 `.py`；实现上述 CLI；按 `ids` 子集检查；语义**不得弱于**对应 `match` 的存在性要求（由 §五 差分冒烟强制，而非口头约束）  
- **材料注入风险**：材料可能含诱导指令；防线 = AST 门 + 差分冒烟 + 导入黑名单（防误用，非防恶意）

## 五、计划链接线

```
clear → normalize → extract_manifest → generate_validator → assess → … → plan
```

### 5.1 `_generate_validator` 步骤

1. **先清旧**：删除已有 `_delivery_validate.py`（若存在）；`Project.delivery_validator_hash = None`（及 generated_at）；flush。避免「新生成失败、旧脚本仍可用」的脏态。  
2. LLM 生成脚本正文（剥 markdown 围栏）。  
3. **静态门（复用 V3 批 C）**：  
   - 优先复用 `project_runtime/skills/install_gates.py` / `sandbox.py` 的 AST 静态检查能力（或抽公共模块），禁止 `subprocess` / `os.system` / `socket` / `requests` / `urllib` / `sqlite3` / `httpx` / `importlib` 等；`ast.parse` 必须成功；须有 `__main__` 入口。  
   - **威胁模型写明**：黑名单挡不住 `__import__`/`exec` 绕过；定位为**防误用**。真隔离：Linux 可可选 bwrap（已有 sandbox 能力）；Windows 以 `-I` + 净化 env + 超时为主，完整隔离另开 ADR。  
4. **差分冒烟（强制，「不得弱于 match」可执行）**：  
   - 临时目录 A：按 manifest 为每个 deliverable 造满足 `match` 的最小假文件 → 脚本 `--ids` 全量 → 必须 `ok=true`。  
   - 临时目录 B：空目录 → 必须 `ok=false`，且每个 id 在 `problems` 中有对应线索（或 problems 条数 ≥ deliverable 数）。  
   - 任一次不满足 → 生成失败。  
5. 写入 `_delivery_validate.py`（先写临时文件再 replace），计算 sha256 → 写 `delivery_validator_hash` + 时间戳。  
6. **任一步失败** → 确保无半成品（清文件 + hash 置空）；**不**继续后续 stage；422 冒泡。

### 5.2 严格失败 + UI（已拍板）

```json
{
  "ok": false,
  "error_code": "DELIVERY_VALIDATOR_INVALID",
  "message": "交付校验脚本生成失败：…"
}
```

- HTTP **422**；`RuntimeEventType.DELIVERY_VALIDATOR_INVALID`。  
- 前端：`PlanningError` 识别 → `antdMessage.error` + 操作区状态文案（与 V1.6c 同路）。  
- 重新「生成计划」= 清场 + 重抽清单 + **先清旧脚本再生成**。

## 六、运行时：收工 Stop + 收口

### 6.1 收工 Stop（Worker）

拟终稿且 `deliverable_ids` 非空：

1. 脚本存在且 `sha256 == Project.delivery_validator_hash`。  
   - **不符（用户选 b）**：记 `DELIVERY_VALIDATOR_TAMPERED`（或复用 INVALID 带 phase=STOP）；**直接视为交付闸失败** → 等价用尽或立即 `DeliveryBaselineError`（文案含「校验脚本被篡改/缺失，请重新生成计划」）→ 任务 **FAILED**。**不**降级 match。  
2. 合法则：

```text
asyncio.create_subprocess_exec(
  sys.executable, "-I", script,
  "--workspace", task_ws,   # data/tasks/{pid}/{tid}
  "--ids", ",".join(ids),
  env=净化且含 PYTHONIOENCODING=utf-8,
  stdout/stderr=PIPE,
)
```

   - **必须异步子进程**，禁止同步 `subprocess.run` 堵事件循环（思维链 / dashboard 会卡）。  
   - timeout 30s；超时 / 非 JSON / 超输出上限 → 当次 problems 注入（计入返工轮次）；连续异常策略与缺件相同（≤3 → FAILED）。  
3. `ok=false` → 注入【收工校验未通过——须返工】；`ok=true` → 归档。  
4. 无 `deliverable_ids`：不跑脚本。  
5. 每次运行记事件 `DELIVERY_VALIDATOR_RUN`（payload：ok / problems 摘要 / 耗时 ms / task_id）便于审计。

**写保护**：file_rw 已禁闭在 `…/{tid}/`，项目根脚本天然不可写；另对 `_delivery_validate.py` 做路径黑名单；确认 shell 工具 cd 逃逸拒绝覆盖项目根写。

### 6.2 收口 Closeout

`_delivery_closeout_check` 改造：

- 有合法冻结脚本 + hash：subprocess，`--workspace data/tasks/{pid}`，`--ids` = 总清单全部 id。  
- 缺项 → 补建「交付补全-{name}」、`deliverable_ids=[该 id]`、submit（同 V1.6c 语义）。  
- 脚本缺失/哈希不符：记事件；**不静默放行**——可跳过自动补建并打 `RECONCILIATION_GAP` + 提示重新规划（与 Stop 篡改同严；避免用脏脚本补任务）。

## 七、架构边界（AGENTS.md）

| 约束 | 做法 |
|--|--|
| Stable Kernel 不被脚本改 | 脚本无 DB；状态仅 Worker/Gate/Closeout 核心路径 |
| 无第三种自动化模式 | 仍 FULL_AUTO / MANUAL |
| 非 DIRECT_STATE_MUTATE | Runtime 核心钩子 |
| Resource Governor | 超时 / 输出上限与 Automation Mode 正交 |
| 预期时延 | 计划链多 1 次 LLM + 差分冒烟，约 **+1～2 分钟**（写入产品说明/忙碌提示即可） |

监督智能体（软质检）**不在本单范围**。

## 八、测试要点

1. 计划：manifest + 脚本合法 → 文件、hash、任务图均有。  
2. AST/违禁导入 / 差分冒烟失败 → 422 `DELIVERY_VALIDATOR_INVALID`，无任务图；前端 toast。  
3. 生成失败后磁盘无残脚本、hash 为空。  
4. Stop：缺产物 → 注入；补齐后通过。  
5. 3 次仍缺 → FAILED。  
6. 篡改脚本 / 删脚本 → 任务 FAILED（不跑 match 降级）。  
7. file_rw / shell 无法改 `_delivery_validate.py`。  
8. 收口：项目根缺项 → 补建 + submit；脚本无效 → 事件且不瞎补。  
9. 子进程 UTF-8 中文 problems 可解析（Windows）。  
10. Dashboard 展示 hash 前缀。
